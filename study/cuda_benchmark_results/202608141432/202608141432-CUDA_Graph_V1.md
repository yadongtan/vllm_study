# CUDA Graph V1 性能测试报告

## 1. 结论

本轮测试验证了 `qwen2_demo_v1.py` 的固定 batch CUDA Graph 实现。默认捕获
`1/2/4/8/16/32` 六张 decode Graph，Prefill 保持 eager，测试请求在 decode
阶段选择能够容纳实际 batch 的最小 Graph。

1、4、8 并发均完成 128/128 请求，失败请求为 0。相对原 Packed CUDA Flash
Attention V2，客户端统计的输出吞吐分别提升 239.8%、159.0% 和 162.8%。
CUDA Graph 明显降低了 decode 的 CPU launch 开销，并将测试期间平均 GPU
利用率提高到约 70%--76%。

当前版本仍明显慢于原生 vLLM，差距随并发增加而扩大：vLLM 吞吐分别是本版本
的 2.31、5.66 和 8.65 倍。主要原因不是 Graph replay 本身，而是 Graph 内每层
仍对固定 2048 长度历史 KV 执行 `index_select`，并通过 PyTorch SDPA 处理完整
固定长度 K/V；它尚未接入直接读取 paged KV 的 attention kernel，也没有 vLLM
的连续批处理调度。

| 并发 | 原 Packed V2 (tok/s) | Paged KV (tok/s) | CUDA Graph V1 (tok/s) | vLLM (tok/s) | vLLM / Graph |
|---:|---:|---:|---:|---:|---:|
| 1 | 47.89 | 46.65 | 162.75 | 375.19 | 2.31x |
| 4 | 89.03 | 83.76 | 230.61 | 1305.21 | 5.66x |
| 8 | 105.55 | 98.66 | 277.39 | 2400.77 | 8.65x |

## 2. 测试口径

- 分支：`vllm_study/v2.0`，包含尚未提交的 CUDA Graph V1 修改。
- GPU：NVIDIA GeForce RTX 4080 SUPER，16376 MiB，驱动 581.29。
- WSL：Ubuntu 24.04。
- 模型：`/opt/models/Qwen2-0.5B-Instruct`，BF16。
- 被测实现：`study/inference_engine/qwen2_demo_v1.py`。
- 服务：`study/openai_server/v3_openai_server.py`。
- Graph batch sizes：`1/2/4/8/16/32`。
- `max_model_len=2048`。
- `max_num_seqs=32` 个真实 cache slots，另有 32 个 padding scratch slots。
- Prefill：eager；Decode：固定 batch CUDA Graph replay。
- 调度批次等待时间：5 ms。
- 并发：1、4、8。
- 每档：128 请求。
- 每请求：固定 1000 token 输入、请求生成 50 token。
- 无限请求速率、忽略 EOS、温度 0。
- 原 Packed V2 对照：`cuda_benchmark_results/202608140213`。
- 原生 vLLM 对照：`cuda_benchmark_results/202608140242`。
- Paged KV 过渡版对照：`cuda_benchmark_results/202608141327`。

| 版本 | 并发 | 成功/失败 | 耗时 (s) | 输出吞吐 (tok/s) | 平均 TTFT (ms) | P99 TTFT (ms) | 平均 TPOT (ms) | P99 TPOT (ms) |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 原 Packed V2 | 1 | 128/0 | 133.63 | 47.89 | 157.18 | 153.73 | 18.09 | 18.39 |
| CUDA Graph V1 | 1 | 128/0 | 38.60 | 162.75 | 57.07 | 57.81 | 6.34 | 35.08 |
| 原 Packed V2 | 4 | 128/0 | 71.89 | 89.03 | 247.45 | 641.03 | 40.76 | 45.79 |
| CUDA Graph V1 | 4 | 128/0 | 27.25 | 230.61 | 404.90 | 744.38 | 11.78 | 74.52 |
| 原 Packed V2 | 8 | 128/0 | 60.63 | 105.55 | 341.45 | 1335.67 | 70.26 | 74.08 |

相对原 Packed V2：

| 并发 | 输出吞吐变化 | 平均 TTFT 变化 | 平均 TPOT 变化 |
|---:|---:|---:|---:|
| 1 | +239.8% | -63.7% | -65.0% |
| 4 | +159.0% | +63.6% | -71.1% |
| 8 | +162.8% | +141.4% | -79.6% |

4、8 并发的 TTFT 上升来自当前固定批次服务的调度方式：一批请求必须完整生成
结束，调度器才处理下一批请求。CUDA Graph 提高了批内 decode 吞吐，但还没有
vLLM continuous batching 在每个 step 接纳新请求的能力，因此排队时间会计入
后续请求的 TTFT。

### 输出 token 统计说明

服务内部每个请求确实执行 50 个生成 token。OpenAI 流式接口将 token ids 解码
为文本，benchmark 客户端再对文本重新 tokenize，因此部分随机输出不能严格
保持一一对应。本轮客户端分别统计到 6282、6284、6283 个输出 token，而理论
生成量均为 6400。上表沿用 `vllm bench serve` 的原始输出吞吐以保持报告口径；
若按服务端实际生成的 6400 token 归一化，吞吐分别为 165.80、234.87、
282.56 tok/s。

## 4. GPU、显存、CPU 和系统内存

| 阶段/并发 | 平均/峰值 GPU | 平均/峰值显存 MiB | 平均/峰值 CPU | 平均/峰值系统内存 MiB |
|---|---:|---:|---:|---:|
| 系统基线 | 12.60% / 13% | 912 / 914 | 0.11% / 0.21% | 1010 / 1013 |
| 服务加载后 | 3.80% / 7% | 5301 / 5304 | 0.05% / 0.09% | 2448 / 2471 |
| 并发 1 | 75.86% / 91% | 5453 / 5478 | 3.52% / 9.25% | 3147 / 3218 |
| 并发 4 | 71.79% / 91% | 6081 / 6232 | 3.69% / 9.24% | 3148 / 3232 |
| 并发 8 | 69.72% / 92% | 7419 / 7836 | 3.79% / 9.26% | 3149 / 3229 |

服务加载后显存约 5.18 GiB，比原 Packed V2 的约 2.55 GiB 高 2.63 GiB，主要
来自固定地址 KV Cache、六张 CUDA Graph 及共享 Graph memory pool。并发从 1
提高到 8 时，峰值显存从 5478 MiB 增至 7836 MiB，说明虽然 Graph 共享 pool，
不同 batch 的 SDPA 和历史 KV gather 仍需要更大的临时 workspace。

原 Packed V2 在 4、8 并发时平均 GPU 利用率约 40% 和 42%；CUDA Graph V1
提高到 72% 和 70%，说明 Python/PyTorch launch 间隙明显减少。CPU 平均利用率
变化不大，仍约为 3.5%--3.8%。

## 5. 当前瓶颈

1. Decode 每层都为每个请求 gather 固定 `max_model_len=2048` 的完整 K/V，短于
   2048 的历史也会产生内存读取和临时 Tensor 开销。
2. SDPA 使用 mask 隐藏未来位置，但固定形状 Graph 仍保留完整 K/V 工作集。
3. 固定批次调度在整批结束前不能插入新请求，高并发时排队 TTFT 较高。
4. 当前 attention 没有直接读取 paged KV cache，仍存在 `index_select + view +
   transpose`。
5. 没有 vLLM 的 continuous batching、paged attention、分级 kernel 选择和更
   完整的 CUDA Graph 调度。

下一步应基于 `qwen2_demo_v1.py`，让 decode attention kernel 直接接收固定地址
KV pages、block table 和 sequence lengths，在 Graph 内按有效历史读取 KV，删除
固定 2048 长度 gather。之后再把 scheduler 改为 step 级请求加入/退出，降低
高并发 TTFT。

## 6. 稳定性记录

正式 benchmark 和服务均正常退出，结果文件及资源汇总完整。服务释放六张
CUDA Graph 后，WSL 实例一度无法响应新命令，`wsl --terminate` 也超时；重启
Windows 的 `WslService` 后恢复，Linux 文件未丢失。该现象不影响已落盘的性能
数据，但后续长时间压测需要继续观察 CUDA Graph 释放阶段的 WSL 稳定性。
