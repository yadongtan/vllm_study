# 202608142355 - 16 与 32 并发性能对比

## 1. 测试结论

本轮在同一台 WSL、同一张 RTX 4080 SUPER 上补测并发 16 和 32。自研版本与原生
vLLM 均完成每档 128 个请求，失败请求为 0。

| 并发 | 自研 output tok/s | vLLM output tok/s | 自研 / vLLM | 吞吐差距 |
|---:|---:|---:|---:|---:|
| 16 | 1818.92 | 2414.44 | 75.3% | -24.7% |
| 32 | 2233.84 | 5720.15 | 39.1% | -60.9% |

从 16 提升到 32 并发时，自研吞吐仅增长 22.8%，vLLM 增长 136.9%。32 并发的主要
差距不是 CUDA Graph batch 形状或单个 Attention kernel，而是 Prefill/Decode 调度方式、
持久 GPU runner 和大 batch 下的整图执行效率。

结合此前同口径的 1/4/8 结果，可以看到完整扩展趋势：

| 并发 | 自研 output tok/s | vLLM output tok/s | 自研 / vLLM |
|---:|---:|---:|---:|
| 1 | 381.00 | 375.82 | 101.4% |
| 4 | 1115.46 | 1342.05 | 83.1% |
| 8 | 1685.51 | 2521.83 | 66.8% |
| 16 | 1818.92 | 2414.44 | 75.3% |
| 32 | 2233.84 | 5720.15 | 39.1% |

1/4/8 来自此前最终最佳自研目录与原生 vLLM 最终目录，16/32 来自本轮目录。由于不是同一次
服务进程中的重复测量，1/4/8 适合观察总体趋势，不应把相邻档位的小幅波动解释为稳定收益；
本轮 16/32 则是在各自同一服务进程内按相同顺序连续完成。

## 2. 测试口径

- 模型：Qwen2-0.5B-Instruct，BF16。
- 每请求 1000 input tokens、50 output tokens。
- 每档 128 请求，`request-rate=inf`，`ignore-eos=true`。
- `max_model_len=2048`。
- `max_num_batched_tokens=2048`。
- `max_num_seqs=32`。
- 原生 vLLM 开启 chunked prefill，`gpu_memory_utilization=0.80`。
- 自研启用异步输出复制、vLLM FlashAttention Paged-KV Decode 和 vLLM fused ops；关闭
  实验性 mixed prefill/decode 与 FlashAttention prefill 路径。
- 自研已捕获固定 batch size 1/2/4/8/16/32 的 CUDA Graph，并按实际 batch 选择最小的
  可容纳 graph。

原始 JSON、资源 CSV、服务日志和复现脚本均在本报告所在目录及 `study/scripts` 中保留。

## 3. 延迟对比

| 并发 | 后端 | 平均 TTFT | P99 TTFT | 平均 TPOT | P99 TPOT | 平均 ITL | P99 ITL |
|---:|---|---:|---:|---:|---:|---:|---:|
| 16 | 自研 | 153.68 ms | 806.53 ms | 7.15 ms | 38.90 ms | 5.55 ms | 29.46 ms |
| 16 | vLLM | 129.92 ms | 391.55 ms | 4.08 ms | 5.62 ms | 4.08 ms | 22.60 ms |
| 32 | 自研 | 199.22 ms | 793.81 ms | 13.16 ms | 79.00 ms | 9.99 ms | 31.91 ms |
| 32 | vLLM | 124.14 ms | 220.05 ms | 3.00 ms | 3.11 ms | 3.13 ms | 6.84 ms |

最关键的证据是并发从 16 增至 32 后：

- 自研平均 TPOT 从 7.15 ms 恶化到 13.16 ms，增加 84.0%。
- vLLM 平均 TPOT 从 4.08 ms 降至 3.00 ms，改善 26.5%。
- 自研平均 TTFT 增至 199.22 ms，vLLM 则降至 124.14 ms。

因此，自研版本没有把新增并发有效转换为 GPU 批处理效率，反而增加了调度和 Prefill
阻塞；vLLM 在 32 并发时才真正把较大的连续 batch 利用起来。

## 4. 为什么高并发下 vLLM 快得更多

### 4.1 自研 Prefill 会暂停整个 Decode batch

当前自研 scheduler 虽然按 `max_num_batched_tokens=2048` 做 admission，但它把每个新请求的
完整约 1000-token prompt 交给单独的 `model.prefill()`。当已有请求正在 Decode 时，新请求的
Prefill 与 Decode 不是同一个 GPU forward：scheduler 先完成 Prefill，所有已有 Decode 请求
在此期间都不能推进。

在该测试口径中，空 batch 最多一次接纳两个约 1000-token prompt；只要已有 Decode 请求，
2048 token budget 通常只能再接纳一个完整 prompt。32 个请求同时在途时，这种串行的
“Prefill 停 Decode”不断制造 GPU 工作阶段切换和长尾延迟。

vLLM 的 chunked prefill 会把 prompt 切成块，并把 Prefill token 与当前 Decode token 放入同一
次调度预算。它不要求先完整跑完一个 prompt 再恢复所有 Decode，而是尽量让每轮接近 2048
token budget，所以请求更多时 GPU 反而更容易持续满载。

### 4.2 vLLM 使用持久化 GPU Model Runner 和输入缓冲区

自研 scheduler 每轮仍在 Python 中维护 `active` 列表，并根据请求变化执行 `torch.cat`、
`index_select`、创建 indices Tensor、同步输出 event 及逐请求状态更新。CUDA Graph 消除了
模型内 kernel launch 的大部分 CPU 开销，但没有消除 graph replay 之间的这些工作。

vLLM 使用持久化 GPU Model Runner、预分配 input/metadata buffer 和异步 scheduler。请求补位、
slot mapping、sequence length、finished 状态和下一轮输入准备不需要每步重新拼接一批临时
Tensor；CPU 调度可与 GPU 执行重叠。并发越高，这一架构差别越明显。

### 4.3 vLLM 捕获的是编译后的完整/分段模型图

自研确实有 batch 32 CUDA Graph，所以本次不是误用了 batch 1 graph，也不是因为 padding 到
更大的 graph。差别在于自研 graph 捕获的仍是学习型 PyTorch 模型路径，内部主要是大量独立
BF16 CUTLASS/cuBLASLt GEMM。此前 profiler 已显示 GEMM 占 Decode GPU 时间约 73.8%。

vLLM 日志确认它使用 `torch.compile`、combo-kernel 优化以及 FULL_AND_PIECEWISE CUDA Graph，
并针对 16/24/32 等 batch capture。它不仅减少 launch，还在编译图中融合模型周边操作并复用
完整 runner metadata。小模型在大 batch 下尤其容易暴露大量小 GEMM 和算子边界的效率差距。

### 4.4 32 并发让 vLLM 的 GEMM 更有效，却让自研调度开销放大

Qwen2-0.5B 的 Decode 在低并发时矩阵乘法的 M 很小，GPU 利用不足。vLLM 在 32 并发时能保持
接近 32 的有效 Decode batch，矩阵乘法形状更适合 GPU，因此每 token 的 TPOT 下降。自研虽然
也有 batch 32 graph，但 Prefill 阻断和请求补位使有效 batch 不稳定，无法长期保持这个形状，
所以 TPOT 反而上升。

### 4.5 KV cache 容量不是本轮吞吐差距的直接原因

自研加载后约占 3.81 GiB 显存；vLLM 按 0.8 利用率预分配后约占 14.22 GiB，并报告约
1,012,560 token 的 KV cache。更大的 page pool 支持更高容量和更灵活的 page 管理，但本轮只有
32 个、上下文约 1050 token 的并发请求，自研 32 slots 足够容纳。因此预分配显存大小不是
2.56 倍吞吐差距的直接来源，关键仍是 runner 和调度执行路径。

空闲样本做事后裁剪。

## 6. 关于自研输出 token 计数

原生 vLLM 每档返回严格 6400 tokens。自研 JSON 中分别统计 6284 和 6285 tokens，这是因为
自研 OpenAI 响应当前没有返回服务端 usage/token_ids，benchmark 对解码后的文本重新 tokenize；
tokenize-decode-tokenize 不保证完全可逆。服务端仍按每请求 `max_tokens=50` 生成，128 个请求
全部成功。即使把自研吞吐按 6400/实际统计 token 数校正，16/32 并发约为 1852.5/2274.7
tok/s，仍只有 vLLM 的约 76.7%/39.8%，不改变结论。

## 7. 下一步最有效的优化

下一步不应继续手写孤立 elementwise kernel，也不应通过等待凑批提高测试数字。最高价值的
工作是把 scheduler 和执行路径重构成持久 GPU runner：

1. 预分配并原位更新 input ids、positions、slot mapping、sequence lengths 和 finished mask。
2. 实现真正的 chunked-prefill 状态机，让 Prefill chunk 与已有 Decode token 共用同一 2048
   token 调度预算和同一个 forward。
3. 将请求补位所需 metadata 原位写入持久 buffer，不在每轮 `torch.cat`/创建临时 Tensor。
4. 在上述 runner 稳定后，再对整模型采用可与外层 graph 协同的 compile/graph partition，重点
   优化占比最高的 GEMM 周边算子。

这是一项整体架构优化，而不是下一枚 Attention kernel；它直接对应本次 32 并发暴露出的
吞吐扩展性问题。
