# 202608150048 - Batch Wait 2 ms

## 1. 结论

本轮只把服务调度器的收批等待窗口从 5 ms 降到 2 ms。并发 1 吞吐提升 2.30%，
但并发 4/8 分别下降 10.94%/2.55%。窗口过短会在并发请求尚未全部进入队列时提前
启动较小 graph batch，因此保留默认 5 ms。

| 并发 | 5 ms 基线 (tok/s) | 2 ms (tok/s) | 变化 | 原生 vLLM (tok/s) |
|---:|---:|---:|---:|---:|
| 1 | 298.28 | 305.13 | +2.30% | 375.19 |
| 4 | 627.42 | 558.79 | -10.94% | 1305.21 |
| 8 | 953.05 | 928.77 | -2.55% | 2400.77 |

## 2. 单一迭代内容

`GraphBatchScheduler._collect_batch()` 取到第一个请求后，会在固定窗口内继续收集请求，
最多达到 32 个真实 cache slots。本轮仅通过 `STUDY_BATCH_WAIT_MS=2` 将窗口从 5 ms
降到 2 ms。

模型、Prefill、Decode、CUDA Graph、KV Cache、Attention 和 D2H 流水均未修改。

## 3. 正确性与完整性

- API 行为和 token 生成路径未改变。
- 1、4、8 并发均完成 128/128 请求，失败请求为 0。
- 每请求固定生成 50 token，忽略 EOS。

## 4. 性能分析

并发 1 本来就只能形成 batch 1，缩短窗口直接减少每轮约 3 ms 等待，因此 TTFT 从
27.80 ms 降到 24.41 ms。并发 4 时，请求到达队列存在轻微抖动，2 ms deadline
会提前封批，导致部分请求使用 batch 1/2 graph，吞吐显著下降。

并发 8 虽然平均 GPU 利用率略升，但较小 batch 的 GEMM 和 Attention 效率更差，不能
用更高 GPU 利用率推断有效吞吐更高。

## 5. 测试口径

- GPU：NVIDIA GeForce RTX 4080 SUPER，16376 MiB。
- 模型：`/opt/models/Qwen2-0.5B-Instruct`，BF16。
- `max_model_len=2048`，`max_num_seqs=32`，Split-KV partition 64。
- `STUDY_PIPELINE_IGNORE_EOS=1`，`STUDY_PIPELINE_STEPS=1`。
- 基线 `batch_wait_ms=5`，本轮为 2。
- 并发 1、4、8；每档 128 请求。
- 每请求 1000 token 输入、请求生成 50 token。
- 无限请求速率、忽略 EOS、温度 0。
- 基线：`cuda_benchmark_results/202608150031`。
- 本轮：`cuda_benchmark_results/202608150048`。

## 8. 决策

默认收批窗口保持 5 ms。若未来要同时优化并发 1 TTFT 和高并发吞吐，应采用“立即
排空当前队列后短暂等待补齐 graph size”的自适应策略，而不是统一缩短固定窗口。
