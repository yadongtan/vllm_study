# 202608150126 - 异步 Tokenizer 并行入队

## 1. 本轮只优化什么

本轮只修改 API 输入处理：把 Hugging Face Tokenizer 从 Uvicorn 的 asyncio
事件循环移到 `asyncio.to_thread` 工作线程。模型结构、CUDA kernel、CUDA Graph、
KV Cache、`batch_wait_ms=5` 和四步 Decode 流水均未改变。

修改文件：

- `study/openai_server/v3_openai_server.py`

新增 `tokenize_prompt()` 和 `prepare_input_ids()`。请求 handler 先异步等待 CPU
tokenization，完成后只在事件循环中把较小的 token id Tensor 搬到 CUDA 并入队。

## 2. 为什么对照 vLLM 后选择这一项

本机原生 vLLM 日志确认实际使用 `FLASH_ATTN`，并启用 vLLM Compile、组合 kernel、
完整/分段 CUDA Graph 和多个固定 graph batch size。当前学习引擎的 Decode profile
为 batch=8、历史长度 1000 时 20 步 GPU kernel 共 61.238 ms，即每步约 3.06 ms；
正式测试的 Decode TPOT 为 3.31 ms，已经接近 GPU profile。

但优化前并发 8 的平均 TTFT 高达 257.36 ms。详细请求时间显示，最初 8 个请求常被
拆成约 3+5 两批：同步 Tokenizer 逐个占用事件循环，第 4 个请求入队前，调度器的
5 ms 收批窗口已经结束。vLLM 的 API 输入处理与引擎调度相互解耦，不会用同步
Tokenizer 阻塞所有其他请求进入调度队列。

因此本轮先解决请求入队，而不是继续改已经接近理论吞吐的 Decode kernel。

## 3. 正确性验证

- `py_compile` 通过。
- 用同一个真实 Qwen2 Tokenizer 比较直接调用和 `prepare_input_ids()`，token id
  完全一致：`[62926, 22243, 45958, 71928, 96, 33956, 33071, 81705]`。
- 1/4/8 并发各完成 128 请求，失败请求均为 0。

## 4. 测试口径

- 模型：Qwen2-0.5B-Instruct，BF16，CUDA。
- 输入/输出：每请求 1000 输入 token、50 输出 token。
- 请求数：每档 128。
- 并发：1、4、8。
- `max_model_len=2048`。
- `max_num_seqs=32`，CUDA Graph batch size 为 1/2/4/8/16/32。
- Split-KV partition=64，四步 Graph enqueue，ignore EOS。
- `batch_wait_ms=5`。
- 优化前基线：`202608150058-Parallel_Split_KV_Merge`。
- 原生 vLLM 基线：`202608140242`。

## 6. 请求分组观察

优化前最初 8 个请求常形成约 3+5 两批。异步 Tokenizer 后，首批前 7 个请求的开始
时间集中在 1.7 ms 内，但第 8 个仍偶尔落入下一批，表现为约 7+1。后续批次也存在
完整 8、7+1 和较小批次混合。

这解释了为什么吞吐显著提升但仍只有 vLLM 的 49.83%：输入事件循环阻塞已经缓解，
固定 5 ms 截止时间和“整批运行到完成”的调度器仍会造成碎片化 batch。

## 8. 结论与后续审计修正

异步 Tokenizer 代码保留，因为它解除 API 事件循环阻塞，与 vLLM 的前端/引擎解耦
方向一致。但本目录的吞吐数据是在旧的固定 5 ms 收批等待和四步 token 聚合下测得，
不得作为移除等待后的正式性能基线，也不能据此证明“凑出完整 batch”是正确优化。

后续正式路线不再等待请求凑批，也不以多 token 聚合交付换吞吐；改为实现真正的
continuous batching 和逐步异步输出处理。
