# 202608150130 - 自适应 Quiet Window 收批

## 1. 本轮只优化什么

本轮只修改 `GraphBatchScheduler._collect_batch()` 的收批截止方式，不修改
Tokenizer、模型、CUDA kernel、CUDA Graph、KV Cache 或 Decode 流水。

旧逻辑从第一个请求到达开始固定等待 5 ms，到点立即结束。新逻辑把 5 ms 解释为
quiet window：每收到一个新请求，就从最后一次到达时间重新等待 5 ms；同时设置
`2 * batch_wait_ms = 10 ms` 的硬上限，防止请求持续零散到达时无限等待。

修改文件：

- `study/openai_server/v3_openai_server.py`

## 2. 为什么这是 vLLM 差距的一部分

异步 Tokenizer 版本已经把并发 8 从约 3+5 改善到常见 7+1，但固定截止时间仍会在
同一波请求尚未全部入队时切批。vLLM 的调度器持续维护 runnable request 集合，并按
token budget 形成下一轮工作，不依赖一个从首请求开始的固定短倒计时。

本轮没有实现完整 continuous batching，只验证“按请求突发的静默期结束收批”能否
减少碎片 batch。

## 3. 正确性验证

- `py_compile` 通过。
- 确定性队列测试中，请求分别在 0/4/8 ms 到达，5 ms quiet window 成功把
  `[1, 2, 3]` 收入同一批，总耗时 8.29 ms；旧固定窗口会在 5 ms 时拆批。
- 1/4/8 并发各完成 128 请求，失败请求均为 0。

## 4. 测试口径

与 `202608150126-异步Tokenizer并行入队` 完全一致：Qwen2-0.5B-Instruct、BF16、
每请求 1000 输入 token/50 输出 token、每档 128 请求、并发 1/4/8、
`max_model_len=2048`、Graph batch size 1/2/4/8/16/32、Split-KV partition=64、
四步 graph enqueue、ignore EOS。

直接基线为 `202608150126`，原始本阶段基线为 `202608150058`，原生 vLLM 为
`202608140242`。

## 6. Batch 分组证据

并发 8 的前 24 个请求形成了三个完整批次：

- 第 1 批 8 个请求 TTFT 均约 406~408 ms；
- 第 2 批 8 个请求 TTFT 均约 104~107 ms；
- 第 3 批 8 个请求 TTFT 均约 103~106 ms。

上轮首批是 7+1，之后也混有较小批次。本轮完整 batch=8 直接解释了 16.76% 的吞吐
提升。并发 4 没有碎片 batch 可消除，quiet window 从最后一次到达重新计时反而增加
少量等待，因此吞吐回退 3.88%。

## 8. 结论（后续审计修正）

本轮拒绝并恢复代码。虽然并发 8 吞吐提升 16.76%，但收益来自等待同一波测试请求
凑成完整 batch=8，并发 4 反而回退 3.88%。这不是 vLLM 的 continuous batching，
也不能改善任意到达率和不同长度请求的通用调度性能。

`202608150134` 和 `202608150138` 是在本实验代码之上完成的后续隔离实验，其数值只
用于各自假设验证，不再视为可累加的正式引擎性能。正式路线改为：请求立即进入
runnable 集合，每一步按 token budget 调度，并允许新请求加入正在 Decode 的集合。
