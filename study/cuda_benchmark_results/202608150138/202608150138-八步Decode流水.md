# 202608150138 - 八步 Decode 流水

## 1. 本轮只优化什么

本轮不改代码，只把 `STUDY_PIPELINE_STEPS` 从默认 4 改为 8。每次 scheduler 进入
ignore-EOS 快速路径后，连续 enqueue 8 次 D2H copy/CUDA Graph replay，再统一等待
event、通知请求和增量 decode 文本。

目标是进一步摊薄 Python 循环、event synchronize、Condition 通知和 tokenizer decode
开销。直接基线为 `202608150130-自适应Quiet_Window收批`。

## 2. 正确性与测试口径

- 模型和所有 CUDA kernel 未改变。
- 1/4/8 并发各完成 128 请求，失败请求均为 0。
- 仍为每请求 1000 输入、50 输出 token，`max_model_len=2048`，ignore EOS。
- 八步流水只影响 token 交付粒度，不改变每一步 graph 的输入 token 依赖关系。

## 3. 性能结果

| 并发 | 四步吞吐 | 八步吞吐 | 变化 | 四步 TPOT | 八步 TPOT |
|---:|---:|---:|---:|---:|---:|
| 1 | 303.62 tok/s | 306.32 tok/s | +0.89% | 3.16 ms | 2.85 ms |
| 4 | 875.93 tok/s | 908.57 tok/s | +3.73% | 3.59 ms | 3.27 ms |
| 8 | 1396.85 tok/s | 1425.70 tok/s | +2.07% | 3.90 ms | 3.58 ms |

吞吐和 TPOT 小幅改善，说明 graph launch/通知摊销仍有少量收益，但幅度只有 1%~4%。

## 4. 流式延迟代价

| 并发 | 四步平均 ITL | 八步平均 ITL | 八步中位 ITL | 八步 P99 ITL | 八步 TTFT |
|---:|---:|---:|---:|---:|---:|
| 1 | 9.76 ms | 16.35 ms | 21.58 ms | 22.70 ms | 46.37 ms |
| 4 | 11.06 ms | 18.73 ms | 24.70 ms | 26.20 ms | 85.82 ms |
| 8 | 12.14 ms | 20.66 ms | 27.24 ms | 28.92 ms | 132.65 ms |

八步流水在交付第一个 token 前也先排入更多 graph replay，所以 TTFT 同样上升。并发 8
吞吐仅提升 2.07%，平均 ITL 却增加 70.14%，中位 ITL 达 27.24 ms，收益不足以覆盖
流式体验回退。

## 6. 结论

本轮拒绝作为默认配置，继续保留 `STUDY_PIPELINE_STEPS=4`。环境变量仍允许离线吞吐
优先场景手动选择 8，但服务默认不以约 70% 的 ITL 回退换取 2% 左右吞吐。

下一轮只移除一个 Prefill 同步点：`Qwen2GraphModel.prefill()` 当前在 CUDA Tensor 上
执行 `torch.all(...).item()` 来判断 prompt 是否等长，而 scheduler 在 CPU 上已经拥有
全部 prompt length。把这个布尔值直接传入模型，可以避免一次不必要的 GPU→CPU
同步，并与 vLLM 在 CPU 调度侧构建 attention metadata 的方式一致。
