# 202608150145 - 无等待、逐 Token 真实基线

## 1. 本轮目的

本轮不是吞吐优化，而是移除两类面向固定并发测试的策略，建立后续架构优化的真实
基线：

1. 调度器不再等待 5/10 ms 凑批，只处理此刻已经在 runnable queue 中的请求；
2. `STUDY_PIPELINE_STEPS` 默认从 4 恢复为 1，每个生成 token 单独交付。

异步 Tokenizer 保留，因为它只解除 API 事件循环阻塞，不等待或聚合请求。

## 2. 行为验证

- `_collect_batch()` 在队列已有一个请求时 0.008 ms 返回，没有等待窗口。
- `--batch-wait-ms` 仅作为旧脚本兼容参数保留，不参与调度。
- 默认 `STUDY_PIPELINE_STEPS=1`。
- `py_compile` 和 `git diff --check` 通过。
- 1/4/8 并发各完成 128 请求，失败请求为 0。

## 3. 测试口径

- Qwen2-0.5B-Instruct，BF16，CUDA；
- 每请求 1000 输入 token、50 输出 token；
- 每档 128 请求，并发 1/4/8；
- `max_model_len=2048`，Graph batch size 1/2/4/8/16/32；
- Split-KV partition=64，ignore EOS；
- 无收批等待，逐 token 输出。

调度架构比较的正式基线。

## 5. 队头阻塞证据

并发 8 的首个请求 TTFT 为 228.5 ms，其他 7 个约 470~472 ms。原因不是请求不足，
而是第一个请求到达后立即进入 run-to-completion：执行 Prefill 和全部 50-token
Decode；其余请求即使已经入队，也只能等待当前请求结束。

随后经常出现 1 个请求先运行、其余请求再组成较大批次的交替模式。当前调度器只在
一整批全部结束后重新读取 incoming queue，这与 vLLM 每个 engine step 都重新选择
runnable work 的 continuous batching 根本不同。

## 7. 下一步

下一轮只实现 continuous batching：

- 没有 active request 时阻塞等待第一个请求，但不额外等待凑批；
- 每个 Decode step 结束后立即 drain 已到达请求；
- 为新请求分配空闲 cache slot 并执行 Prefill；
- 把新请求加入现有 Decode active set；
- 请求完成后立即释放其 KV cache slot。

第一版暂不实现 chunked prefill 或 token budget，避免一次改变多个方向。它解决的是
调度时机和 cache slot 生命周期，不靠延迟请求换 batch 大小。
