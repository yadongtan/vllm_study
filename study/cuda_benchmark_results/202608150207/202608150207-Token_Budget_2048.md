# 202608150207 - Token Budget 2048

## 1. 本轮只优化什么

调度器增加 `max_num_batched_tokens=2048` 的单步准入预算。每次 scheduler
iteration 立即统计当前 Decode token 与等待队列头部完整 Prompt 的 token 数；预算内的
请求马上执行 Prefill，超出预算的请求留在队列中等待下一个 iteration。

这不是等待凑批：没有 quiet window、sleep、deadline、最小 batch 条件，也不会为了增加
batch size 延迟第一个请求。已有请求继续 Decode 时，新请求会在满足 token budget 和空闲
cache slot 的第一个 iteration 立即加入。这与 vLLM scheduler 的 token budget 思路一致。

本轮 Prompt 长度为 1000，Decode 中的每个 active request 占 1 个 token，因此一个
iteration 最多接纳 2 个新 Prompt。当前实现仍一次处理完整 Prompt，尚未实现 chunked
prefill，也没有把 Prefill 与 Decode 合入同一个 forward。

## 2. 正确性与调度验证

- Continuous batching 测试确认：第二个请求能在第一个请求 Decode 期间加入 active set。
- Token budget 测试确认：已有 1 个 Decode token、31 个空闲 slot 时，1000-token Prompt
  单步只接纳 2 个，没有等待计时逻辑。
- 默认 `STUDY_PIPELINE_STEPS=1`，每次只生成并交付一个 token。
- `py_compile`、脚本 `bash -n` 和 `git diff --check` 通过。
- CUDA 1/4/8 并发各完成 128 请求，失败请求为 0。
- 测试后已删除服务端无效的 `--batch-wait-ms` 兼容参数及所有脚本中的旧参数传递，避免
  后续误以为测试仍依赖等待凑批；该参数在本轮测试时已经不参与任何调度判断。

## 3. 性能结果

对比基线为 `202608150203` 的 CUDA Graph Padding 尾部重置版本。

| 并发 | 上一版输出吞吐 | Token Budget | 变化 | 平均 TTFT | 平均 ITL |
|---:|---:|---:|---:|---:|---:|
| 1 | 280.72 tok/s | 281.26 tok/s | +0.19% | 21.22 ms | 3.06 ms |
| 4 | 753.45 tok/s | 734.18 tok/s | -2.56% | 49.84 ms | 4.36 ms |
| 8 | 1104.93 tok/s | 1091.81 tok/s | -1.19% | 66.94 ms | 5.87 ms |

输出吞吐没有改善：并发 4/8 分别下降 2.56% 和 1.19%。并发 8 的平均 TTFT 从
92.46 ms 降至 66.94 ms，下降 27.60%，说明限制单次 Prefill 工作量能够减少新请求被
大 Prefill 阻塞的时间；但平均 ITL 上升，表明当前独立 Prefill forward 仍会打断 Decode。

因此这轮不能记为吞吐优化成功。保留 token budget 是为了建立与 vLLM 一致的调度约束和
控制 Prefill 对在线 Decode 的阻塞，而不是为了制造更大的 batch。真正可能同时改善吞吐和
ITL 的下一步是单独实现 chunked prefill，并让 Prefill chunk 与 Decode token 共享同一
token budget；实现前不增加任何等待窗口。

## 5. 结论

- 禁止恢复固定等待、quiet window 或为测试流量设计的凑批逻辑。
- `max_num_batched_tokens` 只控制立即准入的工作量，不允许用时间条件等待更多请求。
- 本轮主要改善高并发 TTFT，未改善吞吐，性能差距不能靠调度等待掩盖。
- 下一轮若继续，应只实现 vLLM 同类的 chunked prefill/mixed scheduling，并独立测试、
  独立记录；不能同时混入其他 kernel 优化。
