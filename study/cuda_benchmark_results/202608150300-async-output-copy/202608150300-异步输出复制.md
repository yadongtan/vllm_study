# 202608150300 - 异步输出复制

## 1. vLLM 对应优化

vLLM 的 GPU Model Runner 会把 sampled token ids 复制到 pinned CPU 内存，并通过独立
CUDA stream 和 event 延迟等待；GPU 可以继续准备下一轮输入和执行下一次模型 forward。
当前实现此前在默认 stream 上执行 GPU->CPU token copy，然后立即同步 event，导致每个
Decode token 都被 CPU 同步打断。

本轮只实现异步输出复制：

- 复制前先把 CUDA Graph 的输出 token 写入独立 GPU snapshot，避免下一次 replay 覆盖源数据。
- 独立 copy stream 等待 snapshot 完成后，将 token 异步复制到 pinned CPU buffer。
- 默认 stream 不等待 CPU copy，立即 replay 下一轮 CUDA Graph。
- 等下一轮 GPU replay 已经排队后，scheduler 才等待 copy event 并逐 token 交付结果。
- 仍然每轮只交付一个 token，没有 quiet window、固定 batch wait 或多 token 聚合。
- 为保证当前 scheduler 的 EOS 状态机正确，只有整批 `ignore_eos=true` 时启用；普通或混合
  请求自动回退原同步路径。这是 vLLM 异步输出机制的逐步实现，后续可将 finished mask
  也放到 GPU 上以覆盖普通 EOS 请求。

开关：`STUDY_USE_ASYNC_OUTPUT_COPY=1`。

## 2. 正确性验证

- 1/4/8 并发各完成 128 请求。
- 失败请求数均为 0。
- 输出长度仍为 50 token。
- 现有 continuous batching、token budget、padding-tail 单测通过。
- `py_compile`、Shell 语法检查和 `git diff --check` 通过。
- 测试完成后没有残留 server 或 benchmark 进程。

## 3. 性能结果

测试口径：1000 input tokens、50 output tokens、128 requests、`request-rate=inf`，并发
1/4/8，`max_model_len=2048`。基线为 `202608150203` 的 CUDA Graph Padding 尾部重置
版本。

| 并发 | 基线输出吞吐 | 异步输出复制 | 变化 | 基线 TTFT | 新 TTFT | 新平均 ITL |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 280.72 tok/s | 315.48 tok/s | +12.38% | 21.32 ms | 26.75 ms | 2.59 ms |
| 4 | 753.45 tok/s | 878.96 tok/s | +16.65% | 52.72 ms | 51.66 ms | 3.45 ms |
| 8 | 1104.93 tok/s | 1268.37 tok/s | +14.79% | 92.46 ms | 74.93 ms | 4.70 ms |

平均 ITL 和输出吞吐均改善。并发 8 的 TTFT 同时下降 18.97 ms，说明 GPU replay 与
输出复制确实发生了有效重叠。并发 1 的 TTFT 上升 5.43 ms，来自独立 stream、snapshot
和事件启动成本；这属于低并发固定开销，高并发收益更明显。

## 5. 结论与限制

该优化有效，保留。它没有改变请求到达、batch admission 或 token 交付语义，只减少了
GPU replay 等待 CPU token copy 的空洞。

当前限制是 EOS 判断仍依赖 CPU。vLLM 可以在 GPU 上保留 sampled token 和 finished mask，
因此下一步可实现 GPU-side finished-mask/采样状态，覆盖普通 `ignore_eos=false` 请求，
并进一步减少调度同步；实现时仍需保持逐 token 交付。
