# 202608150440 - vLLM Fused Ops 与混合前向累计验证

## 1. 目的

本轮不新增算法，只同时启用以下已独立测试的开关，验证收益能否叠加：

```bash
STUDY_USE_ASYNC_OUTPUT_COPY=1
STUDY_USE_VLLM_FLASH_ATTN=1
STUDY_USE_VLLM_FUSED_OPS=1
STUDY_USE_MIXED_PREFILL_DECODE=1
```

基线是 `202608150420-vllm-fused-ops`，即不启用 mixed Prefill/Decode 的当前最佳版本。

## 2. 结果

| 并发 | Fused ops 最佳基线 | 累计启用 mixed | 变化 | 基线/新 TTFT | 基线/新 ITL |
|---:|---:|---:|---:|---:|---:|
| 1 | 381.00 tok/s | 372.46 tok/s | -2.24% | 20.94 / 24.94 ms | 2.16 / 2.14 ms |
| 4 | 1115.46 tok/s | 1041.33 tok/s | -6.65% | 41.79 / 54.45 ms | 2.69 / 2.69 ms |
| 8 | 1685.51 tok/s | 1569.10 tok/s | -6.91% | 71.19 / 85.85 ms | 3.24 / 3.29 ms |

三档均完成 128/128 请求，失败数为 0，但吞吐全面下降，TTFT 明显上升。因此两项收益
不能在当前实现中直接叠加。

## 3. 分析

混合前向只在请求 admission 阶段执行 eager packed 模型路径。它虽然合并了 Prefill 和
Decode 的权重读取，但也引入了每轮 packed Tensor、位置、slot、`query_start_loc` 和
`sequence_lengths` 的构造，并且这条 eager 路径无法复用纯 Decode CUDA Graph。

vLLM fused ops 已把纯 Decode 时间进一步缩短后，上述 admission 固定开销占比变大；
当前测试只有 50 个输出 token，新请求切换较频繁，因此 TTFT 和总吞吐受到明显影响。
成熟 vLLM 的混合执行依赖持久化 input batch、预分配 metadata buffer 和更完整的 GPU
Model Runner，不能仅用 Python 每轮重新拼接 Tensor 达到同等效果。

## 4. 决策

- `STUDY_USE_MIXED_PREFILL_DECODE` 保留为实验开关，便于继续学习 packed mixed forward。
- 当前最佳性能配置不启用该开关。
- 后续基线继续采用异步输出复制 + vLLM FlashAttention + vLLM fused ops。
- 若继续混合执行，应先实现持久化 metadata buffer 和真正的 chunked prefill 状态机，
  而不是把当前 Python eager 拼接设为默认。
