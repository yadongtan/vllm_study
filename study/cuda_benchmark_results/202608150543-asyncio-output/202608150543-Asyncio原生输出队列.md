# 202608150543 - Asyncio 原生输出队列

## 1. 性能诊断

在上一轮之后，对当前默认最佳版本的 batch-32、position 1000 CUDA Graph Decode 做了 100 步
GPU profiler：总 CUDA 时间为 300.823 ms，即每个 batch-32 Decode step 约 3.008 ms。

原生 vLLM 32 并发平均 TPOT 为 2.998 ms。两者几乎一致，说明当前 batch-32 模型 graph、GEMM
和 Attention 本身已经接近 vLLM；自研服务端平均 TPOT 约 13 ms 的主要差距发生在 graph replay
之间和 HTTP 流式输出链路。

原实现每个请求、每个 token 都执行：

```text
Condition.wait -> asyncio.to_thread -> worker thread -> event loop
```

32 并发每一步会产生最多 32 次线程池任务、Condition 唤醒和事件循环回切。

## 2. 本轮只优化了什么

- 每个 HTTP 请求创建一个 `asyncio.Queue`。
- scheduler 线程仍然逐请求、逐 token 发布结果，没有聚合多个 token。
- scheduler 使用 `event_loop.call_soon_threadsafe()` 将 token 放入对应异步队列。
- 流式和非流式 API 直接 `await` 队列，不再为每个 token 占用 thread-pool worker。
- 保留原 Condition 路径，供无 asyncio event loop 的单测和回退模式使用。

开关：

```bash
STUDY_USE_ASYNCIO_OUTPUT_QUEUE=1
```

默认开启，设为 `0` 可回到原来的 `asyncio.to_thread` 路径。

## 3. 正确性验证

- 验证异步队列依次收到 `([10], False)` 和 `([11], True)`。
- 原 continuous batching、token budget、padding-tail 和 Chunked Prefill 调度测试通过。
- 1/4/8/16/32 每档完成 128 请求，失败数为 0。
- 输出仍逐 token 交付，没有 quiet window 或多 token aggregation。

## 4. 性能结果

测试口径：1000 input、50 output、128 requests、`request-rate=inf`、
`max_model_len=2048`、`max_num_batched_tokens=2048`、`max_num_seqs=32`。
Chunked Prefill 在本轮关闭，以便只测试输出队列变化。

| 并发 | 原默认最佳 tok/s | Asyncio Queue tok/s | 变化 | 新 TTFT | 新 TPOT |
|---:|---:|---:|---:|---:|---:|
| 1 | 381.00 | 370.92 | -2.6% | 25.40 ms | 2.77 ms |
| 4 | 1115.46 | 1023.29 | -8.3% | 51.63 ms | 3.59 ms |
| 8 | 1685.51 | 1578.53 | -6.3% | 67.63 ms | 4.72 ms |
| 16 | 1818.92 | 1972.57 | **+8.4%** | 103.05 ms | 7.63 ms |

32 并发平均 TTFT 从 199.22 ms 降到 164.04 ms，改善 17.7%。吞吐相对 vLLM 从 39.1%
提高到 42.7%。

## 5. 为什么提升没有达到 profiler 的理论值

线程池切换只是输出链路的一部分。当前每个流式请求收到一个 token 后，仍在 Uvicorn 事件循环中：

1. 把 token 追加到该请求的完整 token 列表。
2. 再次调用 tokenizer 解码从第一个 token 到当前 token 的完整列表。
3. 通过字符串前缀长度提取 delta。
4. 为每个请求单独执行 JSON 序列化和 SSE yield。

因此 32 请求 × 50 steps 会产生大量 tokenizer 调用和事件循环任务。scheduler 虽然不再等待
worker thread，但仍与这些 Python 工作争用 GIL；GPU graph 不能持续按 profiler 中的 3 ms
间隔 replay。

低并发回退说明 asyncio queue 的 `call_soon_threadsafe` 固定成本在没有线程池拥塞时不占优势；
它的价值主要出现在 16/32 并发。

## 7. 决策与下一步

保留该优化并默认开启，因为它没有改变推理或流式语义，并在目标高并发场景稳定改善约 9%。
若更重视 1/4/8 并发，可通过环境变量关闭。

下一步对齐 vLLM 的异步输出处理器：使用一个持久化批量 output processor 接收 scheduler 的整批
token 更新，在独立线程中进行增量 detokenize，并以一次 event-loop callback 发布整批结果。
该方向不会等待凑批；它处理的是同一个 GPU step 已经产生的整批 token。
