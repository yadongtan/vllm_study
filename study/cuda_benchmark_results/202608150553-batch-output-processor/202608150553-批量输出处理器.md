# 202608150553 - 持久批量输出处理器

## 1. 本轮优化

本轮尝试对齐 vLLM 的异步 output processor：

- scheduler 每个 GPU step 将整批 token 更新一次性提交到持久工作线程。
- 工作线程负责 tokenizer decode，不再在 Uvicorn event loop 中执行。
- 同一 event loop 每个 GPU step 只执行一次 `call_soon_threadsafe`，然后分发整批结果。
- 每个请求仍逐 token 返回；没有等待、跨 step 聚合或改变生成语义。

开关：

```bash
STUDY_USE_BATCH_OUTPUT_PROCESSOR=1
```

## 2. 正确性

- 单测验证工作线程按顺序产生 `a`、`b` 两个增量文本。
- 1/4/8/16/32 每档完成 128 请求，失败数为 0。
- scheduler 与 output processor 在服务关闭时均完成线程回收。

## 3. 性能结果

| 并发 | Asyncio Queue 基线 | Batch Processor | 变化 |
|---:|---:|---:|---:|
| 1 | 370.92 | 372.17 | +0.3% |
| 4 | 1023.29 | 1050.39 | +2.6% |
| 8 | 1578.53 | 1551.75 | -1.7% |
| 16 | 1972.57 | 2055.41 | +4.2% |
| 32 | 2441.09 | 2389.82 | -2.1% |

相对更早的默认最佳版本，16 并发仍提高 13.0%，32 并发提高 7.0%；但相对紧邻的 Asyncio
Queue 版本，目标 32 并发发生退化，因此不能作为新默认最佳版本。

32 并发平均 TTFT 为 172.35 ms，平均 TPOT 为 12.67 ms；仍远高于纯 batch-32 CUDA Graph
的约 3.01 ms。

## 4. 失败原因

工作线程虽然移除了 event-loop tokenizer 工作，但当前实现仍对每一个新 token 调用：

```python
tokenizer.decode(request.output_ids[:output_length])
```

也就是第 1 步解码 1 token、第 2 步重新解码 2 tokens，直到第 50 步重新解码 50 tokens。
总工作量是 O(output_length²)。把这项工作放入另一条 Python 线程没有消除计算，反而增加了
线程间队列和 GIL 竞争，所以 32 并发下降约 2.1%。

## 5. 决策与下一步

该功能保留为实验实现，但默认关闭：

```bash
STUDY_USE_BATCH_OUTPUT_PROCESSOR=0
```

下一步直接对齐 vLLM 的 `FastIncrementalDetokenizer`。当前环境的 fast tokenizer 支持
`tokenizers.decoders.DecodeStream`，可以让每个新 token 只执行一次 decoder step，将复杂度从
反复完整解码的 O(n²) 降为 O(n)。完成后再重新评估持久 batch output processor。
