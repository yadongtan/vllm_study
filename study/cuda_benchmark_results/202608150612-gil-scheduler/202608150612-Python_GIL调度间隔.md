# 202608150612 - Python GIL 调度间隔实验

## 1. 优化假设

当前 API、流式输出、增量解码器和 GPU scheduler 位于同一 Python 进程的不同线程。
Python 默认约 5 ms 的线程切换间隔可能让 scheduler 已经具备下一次 CUDA Graph replay
输入时，仍需等待处理 SSE 的线程释放 GIL。

本轮新增 `STUDY_PYTHON_SWITCH_INTERVAL_MS`，并以 1 ms 运行。它不等待凑批、不合并
多个 Decode step，也不改变每步生成一个 token 的语义。

## 2. 同口径结果

| 并发 | Fast Incremental 基线 | 1 ms GIL 间隔 | 变化 |
|---:|---:|---:|---:|
| 16 | 2155.08 | 1888.42 | -12.4% |
| 32 | 2536.63 | 2417.39 | -4.7% |

表中为按服务实际生成 6400 token 校正后的 output tok/s。

| 并发 | 时长 (s) | 客户端 tok/s | 校正 tok/s | TTFT (ms) | TPOT (ms) |
|---:|---:|---:|---:|---:|---:|
| 16 | 3.389 | 1865.41 | 1888.42 | 141.81 | 6.89 |
| 32 | 2.647 | 2388.31 | 2417.39 | 193.23 | 11.48 |

## 3. 资源结果

| 并发 | GPU 平均/峰值 | 显存平均/峰值 | CPU 平均/峰值 | 内存平均/峰值 |
|---:|---:|---:|---:|---:|
| 16 | 25.2% / 95% | 3984 / 4035 MiB | 4.28% / 9.18% | 2861 / 3180 MiB |
| 32 | 27.3% / 96% | 4035 / 4035 MiB | 4.95% / 9.03% | 2975 / 3205 MiB |

加载完成、测试前的 GPU/CPU 平均利用率分别为 1.6% 和 0.04%。

## 4. 结论

更频繁的 GIL 抢占增加了线程切换和锁竞争，收益不足以抵消额外开销，因此该实验失败。
开关保留用于诊断，但默认值为 0，即保持 Python 默认线程切换间隔。

这也说明继续微调同进程线程公平性不是正确方向。vLLM 的核心差异是 API server 与
engine core 的进程隔离：HTTP、JSON、SSE 和 detokenization 的 GIL 工作不会阻止 GPU
scheduler 提交下一次模型执行。后续应按这一架构方向迭代。
