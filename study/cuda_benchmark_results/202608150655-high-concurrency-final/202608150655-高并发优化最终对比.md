## 3. 失败或撤销的迭代

| 迭代 | 结果 | 原因 |
|---|---|---|
| 1 ms GIL switch interval | 16/32 均下降 | 线程切换和锁竞争增加 |
| Python Queue 独立 engine 进程 | 16/32 均下降 | pickle/IPC 抵消进程隔离收益 |
| vLLM FlashAttention Prefill | 16/32 均下降 | 等长 SDPA 已高效，packed 转换有额外成本 |

| 两个独立 forward 交错 Prefill/Decode | 32 下降 7.6% | 小 batch Decode 破坏 GEMM 效率 |
| mixed block table 跨层复用 | 下降约 4% | 长生命周期临时量未产生收益 |
| mixed write index 跨层复用 | 16 下降 2.3% | metadata 不是主要热点 |

## 4. 与原生 vLLM 对比

原生 vLLM 结果来自 `202608142355-high-concurrency`，同样使用 1000 input、50 output、
128 requests、`max_model_len=2048`、`max_num_batched_tokens=2048`、`max_num_seqs=32`。

| 并发 | 当前自研 | 原生 vLLM | 自研/vLLM | 剩余差距 |
|---:|---:|---:|---:|---:|
| 16 | 2254.40 | 2414.44 | 93.4% | -6.6% |
| 32 | 2546.50 | 5720.15 | 44.5% | -55.5% |

16 并发已经接近 vLLM；32 并发仍有明显断层。当前 batch-32 Decode CUDA Graph 单步约
3.01 ms，与 vLLM 32 并发 TPOT 2.998 ms 基本一致，因此差距不是单个 Decode kernel。

## 5. 32 并发剩余差距

当前 mixed forward 仍是 Python eager model runner：每个 admission step 动态创建 packed
input、positions、query boundaries、sequence lengths 和 cache-slot Tensor，然后逐层进入
PyTorch dispatcher。vLLM 使用持久化 GPU model runner：

- 预分配并原位更新 input/metadata buffer；
- scheduler 输出直接写入 runner 的固定 buffer；
- mixed Prefill/Decode 复用稳定的 kernel/allocator 状态；
- API server 与 engine core 使用专用共享内存消息协议，而不是通用 Python Queue；
- 输出处理、HTTP/SSE 与 GPU scheduler 不共享同一个 Python GIL 路径。

这些能力是一个整体。此前独立 engine 进程实验已经证明，只加入 Python Queue IPC 会更慢；
metadata 微优化也证明只减少一两个小算子没有意义。下一阶段若继续追近 32 并发 vLLM，
需要建立 `PersistentMixedModelRunner`：固定容量 buffer、原位 metadata 更新、专用 ring buffer
输出协议，并对整个 mixed step 做 profiler/graph 化，而不是继续增加孤立开关。

## 6. 测试口径注意

mixed 版本服务端仍严格生成每档 6400 模型 token。benchmark 对返回文本重新 tokenize 后
记录为 9257--10160，这是 tokenizer decode/encode 非双射导致的统计失真。mixed 版本报告
统一使用 `6400 / duration`；后续 benchmark 工具应直接读取服务端 token 计数或 usage 字段，
避免文本重分词影响 output throughput 与 TPOT。
