# Qwen3.5-4B 1/2/4/8/16/32/64 并发性能对比

测试时间：2026-08-15 18:01  
运行环境：WSL Ubuntu 24.04 + CUDA  
模型：`/opt/vllm_study/models/Qwen/Qwen3.5-4B`  

## 1. 测试对象

- 自研最新版：`study/inference_engine/qwen3_5_demo_v1.py`，由
  `study/openai_server/v3_openai_server.py` 提供 OpenAI 兼容接口。
- 原生 vLLM：当前源码分支构建的 `vllm serve`。
- 两者使用同一个 Qwen3.5-4B 权重和同一个 `vllm bench serve` 客户端。

## 2. 固定测试口径

| 参数 | 值 |
|---|---:|
| 每个请求输入 | 1000 token |
| 每个请求输出 | 50 token |
| 请求总数 | 128 |
| 并发 | 1、2、4、8、16、32、64 |
| `max_model_len` | 2048 |
| `max_num_batched_tokens` | 2048 |
| `max_num_seqs` | 32 |
| dtype | bfloat16 |
| 采样 | temperature=0，ignore-eos |

自研版本启用了 mixed prefill/decode、vLLM FlashAttention、vLLM fused ops
和 fused RoPE/cache write，与上一轮 Qwen3.5 最新版本测试一致。

并发 64 不代表 GPU 内同时运行 64 条序列。由于两套服务的
`max_num_seqs=32`，最多同时执行 32 条，其余请求在调度器中等待。

## 6. 结论

1. 两套实现全部请求成功，Qwen3.5 自研执行器在七档并发下均能稳定运行。
2. 并发 1 时自研达到 vLLM 的 98.4%，固定开销已经比较接近。
3. 并发升高后差距逐步扩大；并发 32 时差 7.1%，并发 64 时差 8.2%。
4. 自研和 vLLM 都在并发 32 附近达到吞吐平台，符合
   `max_num_seqs=32` 的配置预期。
5. 自研峰值吞吐为 363.71 token/s，vLLM 为 393.53 token/s。
6. 自研显存占用比 vLLM 少约 1 GiB，主机内存少约 2.5 GiB，但 vLLM 使用更多
   cache 和运行时工作空间换取了更高的高并发吞吐。
7. 下一阶段要缩小高并发差距，应继续减少 Gated DeltaNet 状态搬运和 Python
   调度开销，并融合 Q/K norm、partial RoPE、cache write 与 GDN gate/state 更新。
