# Qwen3.5-4B 自研、vLLM 与 SGLang 三方性能对比

测试时间：2026-08-15 18:45  
环境：Windows 11 WSL2、Ubuntu 24.04、单张 NVIDIA CUDA GPU  
模型：`/opt/vllm_study/models/Qwen/Qwen3.5-4B`

## 1. 测试结论

1. SGLang 0.5.17 已在独立环境 `.venv-sglang` 中安装并成功运行，七档并发均为 128/128 请求成功。
2. SGLang 的峰值固定工作量吞吐为 383.05 token/s（并发 32）。它比自研峰值 363.71 token/s 高 5.3%，比 vLLM 的 391.44 token/s 低 2.1%。
3. 并发 1/2/4 时 SGLang 略快于 vLLM；并发 8 基本相同；并发 16/32/64 时 vLLM 分别快 3.6%/2.2%/3.3%。
4. SGLang 在并发 32 饱和；并发 64 只增加排队，吞吐从 383.05 降至 380.83 token/s，平均 TTFT 从 1.65 s 增至 4.73 s。
5. 自研引擎在七档并发下均达到 SGLang 的 93.7%～96.0%，并且仅使用约 13.6～14.1 GiB 显存；SGLang 与 vLLM 约使用 14.6～15.2 GiB。

## 2. 安装与运行配置

SGLang 使用独立 Python 环境，未修改项目原 `.venv`：

```text
sglang==0.5.17
sglang-kernel==0.4.5
torch==2.11.0+cu130
Python 3.12
```

固定测试口径：

| 参数 | 值 |
|---|---:|
| 每请求输入 | 1000 token |
| 每请求输出 | 50 token |
| 请求总数 | 128 |
| 客户端并发 | 1、2、4、8、16、32、64 |
| 上下文长度 | 2048 |
| 每轮最大 prefill token | 2048 |
| 引擎最大运行请求 | 32 |
| dtype | bfloat16 |
| 采样 | temperature=0、ignore-eos |

SGLang 参数为 `max-running-requests=32`、`chunked-prefill-size=2048`、
`max-prefill-tokens=2048`、`mem-fraction-static=0.80`。测试使用 Triton
attention 和 Triton GDN/Mamba 后端。

Qwen3.5 的 FP32 GDN 状态较大。SGLang 开启 Radix 前缀缓存时需要为每个请求
预留 5 个状态槽，在 16 GiB 显存上只能并行运行 5 个请求。此次随机输入没有共享
前缀，故使用官方 `--disable-radix-cache`，把无收益的前缀状态快照取消；最终日志
确认分配 32 个 Mamba 状态槽、49,013 个 KV token，并实际允许 32 个运行请求。

## 5. SGLang 请求各阶段耗时

`queue` 和 `forward` 来自 SGLang `ReqTimeStats`；TTFT/TPOT 来自同一客户端。
`decode span` 按 `49 * mean TPOT` 估算，`E2E` 按 `TTFT + decode span` 估算。
这些指标的起止点不同，因此内部 queue+forward 不应与客户端 E2E 强行相加。

| 并发 | 内部 queue 均值 ms | 内部 forward 均值 ms | TTFT ms | 49-token decode span ms | 估算 E2E ms |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.26 | 760.87 | 107.53 | 667.14 | 774.67 |
| 2 | 0.27 | 868.22 | 195.72 | 687.02 | 882.74 |
| 4 | 0.89 | 1074.77 | 312.56 | 788.56 | 1101.11 |
| 8 | 97.61 | 1362.67 | 490.99 | 1005.51 | 1496.50 |
| 16 | 384.48 | 1903.27 | 862.01 | 1502.93 | 2364.94 |
| 32 | 1081.97 | 2702.27 | 1654.89 | 2283.93 | 3938.82 |
| 64 | 4053.21 | 2708.52 | 4727.02 | 2287.13 | 7014.15 |

请求执行顺序及主要耗时来源：

1. HTTP 接收与 tokenizer：将 prompt 转为 1000 个 token，并进入 scheduler 队列。该时间包含在客户端 TTFT，但不完全包含在 SGLang `forward_duration`。
2. Scheduler queue：并发不超过 4 时几乎为 0；并发 32 平均 1.08 s；并发 64 因最多运行 32 个请求，平均等待 4.05 s。
3. Chunked prefill：每批最多 2048 token。高并发日志显示每次通常推进 2 个完整请求加第 3 个请求的部分 token，稳定输入吞吐约 11.3k～11.7k token/s。
4. 首 token：TTFT 包含排队、prefill、第一次采样和 HTTP 流式返回。并发 32 的 1.65 s 中，排队和多轮 chunked prefill 是主要部分。
5. Decode：1/2/4/8 使用 CUDA Graph；大于 8 的主批次使用 eager decode，尾批回落到图。并发 32 日志中的主批 `cuda graph: False`，这是它落后 vLLM 的直接原因之一。
6. Detokenize 与流式输出：SGLang 使用独立 tokenizer/detokenizer 进程和 overlap scheduler，CPU 与 GPU 可部分重叠。

## 8. 性能差异原因

### SGLang 相对自研更快

- SGLang 的 overlap scheduler、tokenizer、detokenizer 和模型 worker 分离，CPU 请求处理、GPU 执行与输出处理重叠得更彻底。
- SGLang 的 Qwen3.5 路径使用专用 Triton GDN kernel、packed decode、预编译/缓存的融合 kernel，并具有成熟的张量复用和调度元数据管理。
- 高并发 prefill 能持续形成约 2048-token chunk，GPU GEMM 形状更稳定。
- 自研仍有 Python scheduler、Python 对象状态维护和更多小 Tensor 元数据操作；在单请求上差距很小，但会随请求数累积。

### vLLM 高并发仍领先 SGLang

- vLLM 使用 FlashAttention 2，并从 torch.compile 缓存加载 AOT 图；本轮 SGLang 因 FlashInfer CUDA 组件版本冲突改用 Triton attention。
- vLLM 捕获 FULL CUDA Graph 到 batch 32；SGLang 本轮默认只捕获 1/2/4/8，16/32 的主 decode 批次为 eager。
- vLLM 的 hybrid KV/Mamba page 规划能提供 69,924 token cache；SGLang 在为 32 个 FP32 状态槽保留显存后剩 49,013 token。
- vLLM 的高并发调度 TTFT 更低；SGLang 更偏向吞吐和 decode 连续性，因此并发 32 的 TPOT 更好，但 TTFT 更高。

### 平台因素

- WSL 下三套客户端均报告 `pin_memory=False`，会削弱异步 CPU/GPU 传输效率。
- SGLang 文本模型启动时仍初始化了多模态依赖；缺少 `libnppicc.so.13` 产生 torchcodec 警告，但文本生成成功，不影响本轮结果正确性。
- `nvidia-smi` 的 GPU 利用率为低频采样，短 prefill/调度空隙会降低高并发均值；应与吞吐和延迟一起看，不能单独作为 kernel 效率结论。

## 9. 自研引擎的性能优化核心特性

1. **Qwen3.5 hybrid 原生执行路径**：按模型结构执行 full attention 与 Gated DeltaNet，避免退化为通用逐层 Python 实现。
2. **固定地址 hybrid cache**：full-attention KV 使用 block/page 形状和 block table；GDN 使用独立 conv 与 recurrent state。请求结束后 slot 可复用，decode 期间不重新分配大 Tensor。它是固定 slot 的 page-shaped cache，不等同于 vLLM 可动态共享的全局 PagedAttention 池。
3. **FP32 GDN 状态**：recurrent state 保持 float32，避免为了显存或测试成绩降低模型状态精度。
4. **Packed/Chunked Prefill**：变长请求按 packed 布局执行，单轮 token 预算为 2048，避免 padding 到最长请求造成无效计算。
5. **Mixed Prefill + Decode**：新请求的 prefill 可与已有请求的 decode 在同一调度步推进，减少纯 prefill 对在线 decode 的阻塞。
6. **Continuous Batching**：请求到达后立即加入活动集合，不等待凑批；完成的 slot 当轮释放并复用。
7. **CUDA Graph Decode**：为 batch 1/2/4/8/16/32 捕获固定图，通过 null slot padding 和固定 cache 地址重放，减少 Python 与 kernel launch 开销。
8. **FlashAttention varlen + block table**：full attention 使用 vLLM FlashAttention 变长接口，不构造大 attention mask，也不显式复制 GQA K/V。
9. **专用 GDN kernel**：prefill 使用 chunk gated delta rule，decode 使用 fused recurrent packed kernel，并使用 causal-conv1d update。
10. **融合算子**：使用 fused add+RMSNorm、RMSNorm、SiLU-and-mul，减少中间 Tensor、显存带宽和 kernel launch。
11. **异步输出路径**：GPU token 先复制到固定 snapshot，再由独立 CUDA stream 复制到 pinned CPU buffer；异步队列和批量 output processor 将 detokenize/HTTP 工作移出 GPU 主循环。
12. **复用调度元数据**：固定 query start、block table、cache slot 与批处理缓冲区，减少每 token 的分配、H2D copy 和 Python 构造。

## 10. 环境问题与处理

1. SGLang 默认 FlashInfer attention 首次 JIT 时检测到 CUDA compiler 与 CCCL/toolkit headers 版本不一致，故改用 SGLang 官方支持的 Triton attention/GDN 后端。
2. Python CUDA 13 包把运行库放在 `cu13/lib`，而 SGLang JIT 固定链接 `cu13/lib64/libcudart.so`。在独立环境中补充 `lib64 -> lib` 和 `libcudart.so -> libcudart.so.13` 兼容链接后，JIT 与 CUDA Graph 捕获成功。
3. 初始 Radix 配置只能运行 5 个请求。关闭本次随机工作负载无法命中的 Radix cache，并将 Mamba/full-cache 比例设为 1.0 后，日志确认 `max_running_requests=32`。
