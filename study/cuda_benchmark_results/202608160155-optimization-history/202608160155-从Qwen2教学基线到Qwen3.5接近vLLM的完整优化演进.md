# 从 Qwen2 教学基线到 Qwen3.5 达到 vLLM 90%+ 的完整优化演进

生成时间：2026-08-16 01:55 CST

代码分支：`vllm_study/v2.0`

主要设备：NVIDIA GeForce RTX 4080 / 4080 SUPER，WSL Ubuntu 24.04，CUDA，BF16

主要源码：`study/inference_engine`、`study/openai_server`、`study/inference_engine/cuda_attention`

## 1. 摘要

这份报告复盘了项目从最初的 Qwen2 教学实现，到 Qwen2 CUDA 推理引擎，再到
Qwen3.5-4B 专用 Hybrid 执行器的完整性能演进。结论不是“换一个更快的 Attention
算子就接近 vLLM”，而是必须同时解决以下五层问题：

1. **计算布局**：取消 GQA K/V 复制、跨请求 dense QK、无效 tile 和大 mask。
2. **缓存布局**：从每 token `torch.cat` 迁移到固定地址的 Paged KV 与 Hybrid state。
3. **GPU 执行**：CUDA Graph、Direct Paged Attention、Split-KV、成熟 FlashAttention
   与融合算子共同降低 launch、访存和长 KV 串行扫描开销。
4. **调度和输出**：Continuous Batching、Mixed/Chunked Prefill、持久元数据、异步
   D2H、增量 Detokenize 和输出线程把 CPU 工作移出 GPU 关键路径。
5. **模型专用路径**：Qwen3.5 不能套用纯 Qwen2 全注意力执行器；24 个 Gated
   DeltaNet 层需要固定 recurrent/conv state 和专用 Prefill/Decode kernel。

最终 Qwen3.5-4B 自研执行器在 1/2/4/8/16/32/64 并发下达到同机 vLLM 的
`98.4% / 94.7% / 96.1% / 94.8% / 93.4% / 92.9% / 91.8%`。这才是本报告中
“达到 vLLM 90% 以上”的严格含义。

Qwen2 阶段不能被改写成“所有并发都达到 90%”：并发 16 曾达到 vLLM 的 93.4%，
但并发 32 仅为 44.5%。这个断层揭示了当时 Python mixed runner、元数据构造与
调度架构仍不完整，也是后来继续实现持久 buffer 和 Qwen3.5 专用路径的直接原因。

## 4. 从完整历史重算到变长连续批处理

### 4.1 v0：每生成一个 token 都重算完整历史

最初版本的价值是把 Qwen2 的权重融合、RoPE、GQA、RMSNorm 和生成循环完整地
写出来。它尚未实现服务引擎最基本的 KV Cache。

优化前（提交 `ea6511f82`，原源码，省略停止条件）：

```python
token_ids = input_ids

for _ in range(max_new_tokens):
    next_token = model(token_ids).argmax(dim=-1)
    token_ids = torch.cat((token_ids, next_token[:, None]), dim=1)
```

Attention 每轮接收的是从提示词开头到当前位置的完整序列：

```python
attention = F.scaled_dot_product_attention(
    query,
    key,
    value,
    dropout_p=0.0,
    is_causal=True,
)
```

若提示词长度为 `P`，生成长度为 `D`，Decode 阶段会依次重算长度
`P, P+1, ..., P+D-1` 的所有层。过去 token 的 K/V 以及它们之前的 Transformer
计算都被反复执行。MPS 口径下，c1/c4 只有 `1.4506/1.4491 tok/s`，并发 4
几乎没有吞吐增益。

vLLM 从来不会在普通自回归 Decode 中这样重算。其模型 runner 会把已计算 token
对应的 KV 写入缓存，调度器只为尚未计算的 token 安排工作。

### 4.2 v1：逐层 KV Cache，Decode 只输入一个 token

优化后（提交 `23735fb6a`，原源码，删去日志）：

```python
if start_position > 0:
    k_cache = request_cache[KVCacheType.K][layer_index]
    v_cache = request_cache[KVCacheType.V][layer_index]
    key = torch.cat((k_cache, key), dim=2)
    value = torch.cat((v_cache, value), dim=2)

request_cache[KVCacheType.K][layer_index] = key
request_cache[KVCacheType.V][layer_index] = value

attention = F.scaled_dot_product_attention(
    query,
    key,
    value,
    attn_mask=attention_mask,
    dropout_p=0.0,
    is_causal=attention_mask is None,
)
```

生成循环也从“每轮输入完整历史”改成“Prefill 输入提示词，Decode 只输入末尾
一个 token”：

```python
if decode_index == 0:
    logits = model(token_ids, ids, [0], kv_cache_manager, prefill_len)
else:
    logits = model(
        token_ids[:, -1:],
        ids,
        [prefill_len + decode_index - 1],
        kv_cache_manager,
        1,
    )
```

这一步让 MPS c1 从 `1.4506` 提升到 `3.1734 tok/s`，增加 118.8%；c4 从
`1.4491` 提升到 `2.4745 tok/s`，增加 70.8%。改进来自取消历史 token 的
QKV 投影、MLP 和层间计算，而不是 Attention 可以忽略历史 KV。普通全注意力的
每个 Decode query 仍必须读取其全部有效历史 K/V。

这一版仍有三个明确问题：

1. `repeat_interleave` 在写 Cache 前把 2 个 KV head 复制成 14 个 head，失去 GQA
   节省显存和带宽的意义。
2. 每次 `torch.cat` 都分配更大的 Tensor 并复制整个历史，复杂度随序列增长。
3. `batch_size=1` 的限制使多个请求仍不能共享一次模型前向。

vLLM 的等价目标是 KV Cache，但实现不是 Python 字典加 `torch.cat`，而是
`KVCacheManager`、`BlockPool`、`slot_mapping` 和固定物理 Block。

### 4.3 v2：Packed 变长请求、Continuous Batching 与 Chunked Prefill

v2 把同一调度 step 中各请求的 token 沿 token 维拼接：

```python
query_start_loc = [0]
input_id_chunks = []

for request in running_list:
    current_tokens = request.get_current_pd_token()
    input_id_chunks.append(current_tokens)
    query_start_loc.append(query_start_loc[-1] + current_tokens.shape[0])

input_ids = torch.cat(input_id_chunks, dim=0)
batch_logits = model(
    input_ids=input_ids,
    ids=running_list,
    query_start_loc=query_start_loc,
    kv_cache_manager=kv_cache_manager,
)
```

`query_start_loc=[0, 4, 6, 7]` 表示 packed Tensor 中 `[0,4)` 属于请求 0，
`[4,6)` 属于请求 1，`[6,7)` 属于请求 2。所谓“变长请求”，就是同一 step
中每个请求实际处理的 query token 数和历史 KV 长度都可以不同，例如一个请求
Prefill 512 token，另两个请求各 Decode 1 token。

调度器不再让一个请求独占完整生成周期，而是在 `max_batch_num_tokens` 预算内先
推进 running 请求，再接纳 waiting 请求；长提示词最多取
`chunk_prefill_tokens`。这是 Continuous Batching 和 Chunked Prefill 的第一版。

然而 v2 为了继续调用普通 SDPA，把所有请求 K/V 拼成一个大 Tensor，再创建全局
二维 Mask：

```python
key = torch.cat(full_key_chunks, dim=1)
value = torch.cat(full_value_chunks, dim=1)

attention_mask = torch.zeros(
    query.shape[1],
    key.shape[1],
    dtype=torch.bool,
    device=hidden_states.device,
)

for request in requests:
    attention_mask[
        request.q_begin : request.q_end,
        request.kv_begin : request.kv_end,
    ] = request.causal_mask

attention = F.scaled_dot_product_attention(
    query,
    key,
    value,
    attn_mask=attention_mask,
)
```

Mask 保证了数学结果正确，却不保证底层不计算被遮掉的元素。总矩阵仍是
`sum(q_len) * sum(kv_len)`，有效计算只是 `sum(q_len_i * kv_len_i)`。无效部分
包括不同请求之间的 Q/K 组合；请求越多、长度越不均匀，浪费越大。

因此 MPS v2 的 c1 从 v1 的 `3.1734` 增至 `4.8674 tok/s`，但 c4 从
`2.4745` 降至 `1.8764 tok/s`。这不是 Continuous Batching 本身无效，而是
Continuous Batching 暴露了 Attention 后端不支持真正 varlen 请求的问题。

vLLM 的调度器同样按 token budget 工作，但后端通过 `cu_seqlens_q`、
`seqused_k` 和 `block_table` 调用 Varlen/Paged Attention，不构造这个全局 dense
Mask。

### 4.4 请求结束立即释放 KV Cache

早期调度器把结束请求移出 `running_list`，却遗漏了 KV 字典中的条目。完成请求越
多，旧 K/V Tensor 保留越多，最终导致显存增长、allocator 压力甚至 OOM。

修复前：

```python
if request.finished:
    finished_list.append(request)
```

修复后（提交 `3d0ac18ca`，原源码）：

```python
if request.finished:
    self.kv_cache_manager.pop(request.req_id, None)
    self.finished_list.append(request)
```

这是一项正确性和资源生命周期修复，不把它单独包装成算子吞吐提升。动态
`PagedKVCache` 版本会归还请求的物理 Page；后期静态 Graph Cache 归还的是整个
scheduler slot，固定 Page 区间随后由新请求覆盖复用；Qwen3.5 Hybrid slot 还同时
代表 GDN state 区间。vLLM 对应 `KVCacheManager.free` 与
`BlockPool.free_blocks`。

## 5. 从 Dense SDPA 到有效 Packed CUDA Attention

### 5.1 CUDA SDPA 基线和“公式原样搬运”

Qwen2 CUDA 基线仍使用 PyTorch SDPA，c1/c4/c8 为
`50.04/87.68/83.69 tok/s`。第一版自定义 Ragged GQA kernel 的目的不是立即
超过 PyTorch，而是先验证以下数学公式和变长边界：

```text
score(q, k) = dot(q, k) / sqrt(head_dim)
probability = softmax(score)
output = sum(probability * value)
```

等价精简代码：

```cpp
int q_token = blockIdx.x;
int q_head = blockIdx.y;
int kv_head = q_head / group_size;

int request = find_request(query_start_loc, q_token);
int visible_len = past_lens[request] + q_local + 1;

for (int kv_local = threadIdx.x;
     kv_local < visible_len;
     kv_local += blockDim.x) {
    scores[kv_local] = dot(
        query[q_head][q_token],
        key[kv_head][kv_start + kv_local]
    ) * scale;
}

block_softmax(scores, visible_len);

for (int dim = threadIdx.x; dim < head_dim; dim += blockDim.x) {
    output[q_head][q_token][dim] = weighted_sum(scores, value, dim);
}
```

这里 `grid=(total_query_tokens, num_query_heads)`，一个 CTA 负责一个 query token
的一个 query head。`kv_head=q_head/group_size` 直接映射共享的 GQA KV head，
不再显式复制 K/V。

结果为 `29.70/65.73/81.80 tok/s`。严格同轮 SDPA A/B 是
`37.39/68.35/68.26 tok/s`，因此变化为 -20.6%/-3.8%/+19.8%。3.2 总表中的
`50.04/87.68/83.69` 来自另一轮初始 CUDA 快照，只用于时间线，不能拿来做这一项
kernel 的严格归因。低并发回退是预期的：公式正确不等于 kernel 高效。朴素实现
缺少成熟 SDPA 的矩阵分块、向量化 load、warp 归约、online softmax、双缓冲和
架构特化。

### 5.2 FlashAttention V1：每个线程负责一个 Query，仍串行扫描全部 Packed KV

V1 首次引入分块 online softmax，避免落地完整 Attention 矩阵，但它尚未沿 KV
长度增加 grid 并行度。原始启动结构为：

```cpp
int num_q_blocks = ceil_div(seq_len_q, q_block_size);
dim3 grid(num_q_blocks, batch_size, num_q_heads);
dim3 block(q_block_size, 1, 1);
```

一个线程负责一个 query token 的一个 head，并在该线程内遍历整个 packed
`kv_seq_len`：

```cpp
int q_token = blockIdx.x * blockDim.x + threadIdx.x;
int request = find_request(query_start_loc, q_token);

for (int kv_block = 0;
     kv_block < total_kv_tokens;
     kv_block += kv_block_size) {
    for (int kv_token = kv_block;
         kv_token < kv_block + kv_block_size;
         ++kv_token) {
        float score = dot(query[q_token], key[kv_token]) * scale;
        if (!belongs_to_and_visible_by(request, kv_token)) {
            score = -INFINITY;
        }
        online_softmax_update(score, value[kv_token]);
    }
}
```

它保留请求边界并得到正确结果，却仍让每个 query 线程扫描**所有请求拼接后的 KV**。
跨请求元素最后被设为 `-INFINITY`，但点积、地址计算和循环已经发生；同时单线程还
串行计算 `head_dim` 点积与输出维度，无法利用 tensor core 或充分的 warp 协作。

性能降到 `13.90/11.06/8.19 tok/s`。即便 GPU 利用率接近 95%，也只说明大量
低效线程持续占用 GPU，不代表有效吞吐高。这一版不作为性能路径保留。

### 5.3 FlashAttention V2：Q/K 二维 Tile 并行，但仍是全局矩形 Grid

V2 才首次沿 K/V 长度增加 grid 维度：

```cpp
dim3 grid(num_q_blocks, num_kv_blocks, num_query_heads);
dim3 block(threads, 1, 1);
```

一个 block 计算一个 `Q tile × KV tile`，把局部 softmax 统计量写入 FP32 workspace：

```python
partial_max = empty([num_heads, total_q, num_kv_blocks], float32)
partial_sum = empty([num_heads, total_q, num_kv_blocks], float32)
partial_o = empty(
    [num_heads, total_q, num_kv_blocks, head_dim],
    float32,
)
```

第二个 kernel 再按 query row 合并所有 KV tile。K 维并行和 warp reduction 让性能从
V1 恢复到 `47.91/53.43/37.04 tok/s`，提升 244.7%/383.1%/352.3%。

但 grid 仍是全局 `num_q_blocks × num_kv_blocks` 笛卡尔积。它会启动“请求 A 的
Q tile × 请求 B 的 KV tile”，靠 Mask 将其 partial 变成空结果；workspace 还为
每个 query 预留全局 `num_kv_blocks`，产生大量无效 FP32 partial。c8 只有
37.04 tok/s 正是这个结构在高并发下扩张的结果。

### 5.4 Packed Valid Tile：保留变长边界但不拆成小 Tensor

Packed V2 才在 host 端按请求生成有效工作项：

```python
valid_tiles = []

for request_id in range(num_requests):
    for query_tile_id in request_query_tiles(request_id):
        for key_tile_id in causally_visible_key_tiles(
            request_id,
            query_tile_id,
        ):
            valid_tiles.append(
                (request_id, query_tile_id, key_tile_id)
            )
```

CUDA grid 改为 `grid=(num_valid_tiles, num_query_heads)`；`blockIdx.x` 直接索引一个
属于同请求的 Q/KV tile，不再代表全局矩形坐标：

```cpp
TileWork work = valid_tiles[blockIdx.x];
int request_id = work.request_id;
int query_begin = query_start_loc[request_id]
                + work.query_tile_id * query_tile_size;
int key_begin = kv_start_loc[request_id]
              + work.key_tile_id * key_tile_size;
```

数据本身继续保留 packed Q/K/V 与前缀和：

```text
query = [request_0_q | request_1_q | ...]
key   = [request_0_kv | request_1_kv | ...]

query_start_loc = [0, q0, q0+q1, ...]
kv_start_loc    = [0, kv0, kv0+kv1, ...]
```

每个工作项只存紧凑元数据，kernel 通过前缀和得到真实地址。它同时做到：

- 不创建每请求独立 Tensor；
- 不显式复制 GQA K/V；
- 不计算跨请求 Q/K；
- Chunked Prefill 和 Decode 都使用同一套变长边界。

性能从 V2 tiled 的 `47.91/53.43/37.04` 变为
`47.89/89.03/105.55 tok/s`。c1 基本不变，c4/c8 提升 66.6%/185.0%，峰值显存
从 8819 MiB 降至 3091 MiB。收益来自高并发时更少的中间 Tensor、partial 和
无效 tile，而非改变 Attention 数学公式。

vLLM 的 `FlashAttentionImpl.forward` 同样把 `query_start_loc` 作为
`cu_seqlens_q`，把有效 K 长度作为 `seqused_k`，并传入 `block_table`。目标与
本设计一致，但 vLLM/FlashAttention 并不等价于这份 Python 生成的 Tile 列表。

## 6. Paged KV Cache：先获得固定地址，再消除 Gather

### 6.1 为什么连续 Cache 的 `torch.cat` 无法扩展

连续 Cache 每个 Decode step 都做：

```python
all_key = torch.cat((cached_key, current_key), dim=token_dim)
all_value = torch.cat((cached_value, current_value), dim=token_dim)
request_cache[layer] = (all_key, all_value)
```

长度从 `L` 增至 `L+1` 时需要重新分配并复制 `L` 个历史 token。地址不断变化，
也无法把读取这些 Tensor 的整段模型捕获进稳定 CUDA Graph。

### 6.2 固定物理 Page、逻辑 Block Table 和 Slot Mapping

Paged KV 把一个大 Cache Buffer 切成固定大小物理 Page：

```text
物理 Cache：page 0 | page 1 | page 2 | ... | page N
请求 A Block Table：[7, 2, 19, ...]
请求 B Block Table：[5, 11, ...]
```

请求的逻辑第 0 页可以映射到物理 page 7，第 1 页映射到 page 2。增长只需从
free list 取一个新 page 并追加 block id，不移动已有 KV。`slot_mapping` 则把
本轮每个新 token 映射到 `physical_page * page_size + page_offset`。

等价精简代码：

```python
slots = slot_mapping[:num_new_tokens]
key_cache.view(-1, num_kv_heads, head_dim)[slots] = current_key
value_cache.view(-1, num_kv_heads, head_dim)[slots] = current_value
```

项目先用一轮满足 `max_num_batched_tokens` 的假请求完成 PyTorch/CUDA lazy
初始化，再按以下预算分配 KV Cache：

```text
target_memory = GPU 总显存 * gpu_memory_utilization
activation_reserve = max(0, 预热峰值 - 当前进程保留显存)

budget_available = target_memory - 预热峰值
physically_available = 当前空闲显存 - activation_reserve
KV 可用字节数 = max(0, min(budget_available, physically_available))
可分配 Page 数 = floor(KV 可用字节数 / 单 Page 字节数)
```

同时受“进程目标利用率”和“机器当前真实空闲显存”限制，避免其他 GPU 进程存在时
仍按理论总量过度分配；`activation_reserve` 为后续 Prefill 保留预热时观测到的峰值。

这里描述的是 `study/inference_engine/paged_kv_cache.py::PagedKVCache` 过渡版：
它不会为每个请求预留 `max_model_len` 的独占 Cache，请求只从全局 free list 取得
当前长度需要的 Page；`max_model_len` 只约束单请求上限。vLLM 采用同类全局
Block Pool。

后续为了用最直接的方式教学 CUDA Graph，`qwen2_demo_v1.py::StaticBatchKVCache`
改用了更严格的静态映射：

```python
max_blocks_per_slot = ceil_div(max_model_len, block_size)
num_total_slots = max_num_seqs + max_graph_batch_size
num_blocks = num_total_slots * max_blocks_per_slot
block_table = arange(num_blocks).view(
    num_total_slots,
    max_blocks_per_slot,
)
```

这意味着每个真实 slot 和 Graph scratch slot 都固定拥有 `max_model_len` 对应的
Page 区间；短请求也不能把未使用 Page 借给别的 slot。Qwen3.5 最终
`Qwen3_5HybridCache` 同样为每个 real/null slot 固定预留 full-attention pages，只是
它只有 8 个 full-attention 层且所有 padding row 共用一个 null slot。这个静态方案
易于学习和捕获，但**不是** vLLM 的动态 BlockPool，也不是 CUDA Graph 的必要条件。

### 6.3 过渡版 Gather 为什么吞吐先下降

第一版虽然写入 Paged Cache，Attention 前仍把离散 Page 收集成连续 Tensor：

```python
page_ids = block_table[request_id, :num_pages]
continuous_key = key_pages.index_select(0, page_ids).reshape(...)
continuous_value = value_pages.index_select(0, page_ids).reshape(...)
output = attention(query, continuous_key, continuous_value)
```

`index_select/gather` 的含义是按照索引从源 Tensor 读取离散元素，并把它们写入一个
新的连续 Tensor。这里等于完整读取一遍 KV、写临时 Tensor，Attention 随后再读
一遍；同时增加 allocator 和 kernel launch。

因此 Packed Tile 的 `47.89/89.03/105.55` 下降为
`46.65/83.76/98.66 tok/s`，分别回退 2.6%/5.9%/6.5%。这一步保留的价值是
内存生命周期、固定地址和后续 Graph 基础，不是当场提升吞吐。

vLLM 对应组件是 `KVCacheManager.allocate_slots/free`、`BlockPool` 与
`reshape_and_cache_flash`。成熟路径不会在每个 Decode step 用 Python
`index_select` 还原完整历史。

### 6.4 Direct Paged Attention：在 kernel 内按需寻址

优化后，Attention kernel 直接从 Block Table 找到某个逻辑 KV token：

```cpp
int logical_page = kv_token_index / page_size;
int page_offset = kv_token_index % page_size;
int physical_page = block_table[
    request_id * max_pages_per_request + logical_page
];

const scalar_t* key_ptr = key_cache
    + physical_page * page_stride
    + kv_head * head_stride
    + page_offset * token_stride;
```

没有连续 KV 副本。相对 CUDA Graph V1，c1 从 162.75 降到 138.70 tok/s，
c4 从 230.61 增至 235.71，c8 从 277.39 增至 337.21。单并发的页表寻址和自定义
kernel 固定成本大于收益；并发 8 的 KV 读取量更大，避免 gather 后提升 21.6%。

vLLM 的 FlashAttention/PagedAttention kernel 同样直接消费 `block_table` 和物理
K/V Cache；对应接口在 `vllm/v1/attention/backends/flash_attn.py`，底层教学
参考可见 `csrc/libtorch_stable/attention/attention_kernels.cuh`。

## 7. CUDA Graph：固定的是执行拓扑与地址，不是 KV 有效长度

### 7.1 Eager 热路径的成本

优化前每个 Decode step 都重新经过 Python module 调用、数十层 kernel launch、
临时 Tensor 创建和 allocator 路径：

```python
input_ids = torch.cat(step_tokens)
metadata = build_metadata(requests)
logits = model(input_ids, metadata)
sampled_ids = torch.argmax(logits, dim=-1)
```

Qwen2-0.5B 的单个 kernel 很短，小 batch 时 CPU 提交开销占比尤其高。

### 7.2 固定 Batch Bucket 捕获和重放

当前 `FixedBatchCUDAGraph` 的等价精简代码是：

```python
static_input_ids = torch.empty(
    graph_batch_size,
    dtype=torch.long,
    device="cuda",
)
static_positions = torch.empty(
    graph_batch_size,
    dtype=torch.long,
    device="cuda",
)
static_cache_slots = torch.empty(
    graph_batch_size,
    dtype=torch.long,
    device="cuda",
)

graph = torch.cuda.CUDAGraph()
with torch.cuda.graph(graph):
    static_logits = model.decode(
        static_input_ids,
        static_positions,
        static_cache_slots,
        cache,
    )
```

运行时只原地更新固定 Buffer 的内容并 replay：

```python
static_input_ids[:batch_size].copy_(runtime_input_ids)
static_positions[:batch_size].copy_(runtime_positions)
static_cache_slots[:batch_size].copy_(runtime_cache_slots)
graph.replay()
```

项目为默认 `1/2/4/8/16/32` 捕获独立 batch bucket。真实 batch 选择能容纳它的
最小 bucket，多余行使用 scratch slot/padding。Graph replay 期间 kernel 的 grid、
block、动态 shared memory 大小和 launch 顺序与捕获时一致。

KV 有效长度仍可变化，因为物理 K/V Buffer 的地址和最大形状固定，kernel 从
`positions`/sequence metadata 读取实际长度。当前教学实现的 slot-to-page 映射本身
固定；vLLM 则允许把新的物理 block id 原地写入固定形状 `block_table`，Graph 仍然
有效。换言之，Graph 固定“容器地址与启动拓扑”，没有要求每个请求有效历史长度
相同，也没有要求每请求永久拥有固定物理 Page。

CUDA Graph V1 还没有按有效长度优化 Attention：它每层 gather 固定
`max_model_len=2048` 的完整 K/V，再用 Mask 隐藏未来位置。后续 Direct Paged/
Split-KV kernel 才根据实际 `positions` 跳过无效历史。因此本轮跃升来自减少 Python
launch，而不是已经解决了 KV 工作量。

Paged KV 过渡版到 CUDA Graph V1 从 `46.65/83.76/98.66` 跃升到
`162.75/230.61/277.39 tok/s`，提升 248.9%/175.3%/181.2%。这是整个链条第一项
架构级跃升。

vLLM 的对应设计包括 `CudagraphDispatcher`、`BatchDescriptor`、
`_compute_bs_to_padded_graph_size` 和 `CUDAGraphWrapper`，本质同样是静态输入
Buffer、batch bucket 与 replay。

## 8. Split-KV Partition Attention：让长历史产生更多并行工作

### 8.1 单 CTA 扫完整历史的问题

Direct Paged Attention 最初使用：

```cpp
// grid = (batch_size, num_query_heads)
for (int kv_index = 0; kv_index < sequence_length; ++kv_index) {
    float score = dot(query, key[kv_index]) * scale;
    update_online_softmax(score, value[kv_index]);
}
```

一个 block 唯一对应 `(request, query_head)`。这里的一个 query 是一个 token 的
一个 attention head，而不是整个 token 的全部 heads。10 个 Decode 请求、14 个
query heads 会产生 `10 * 14 = 140` 个 block；`batch_size` 指同一 Graph step 的
请求槽位数，不会始终等于 1。

但无论历史 KV 是 64 还是 2048 token，这个 `(request, head)` 仍只有一个 block
顺序扫描。长历史下并行度和 latency 都受限。

### 8.2 沿 KV 再增加 Partition 维

优化后：

```cpp
// grid = (batch_size, num_query_heads, max_partitions)
int begin = partition_id * partition_size;
int end = min(begin + partition_size, sequence_length);

PartialResult partial = attention_partition(
    query,
    key_cache,
    value_cache,
    block_table,
    begin,
    end
);
```

每个 partition 保存 `head_dim + 2` 个 FP32 数，源码中的实际顺序为：

```text
[0]              局部最大 logit m_i
[1]              l_i = sum(exp(score - m_i))
[2 : 2+head_dim) 未归一化分子 n_i
                   = sum(exp(score - m_i) * value)
```

第二个 kernel 用稳定 softmax 合并：

```python
global_max = max(partition_max)
correction_i = exp(partition_max_i - global_max)
global_numerator = sum(partition_numerator_i * correction_i)
global_denominator = sum(partition_exp_sum_i * correction_i)
output = global_numerator / global_denominator
```

不能直接平均各 partition 输出，也不能把未归一化分子再乘一次 `l_i`；`l_i` 只参与
全局分母。`head_dim + 2` 正是为了保存合并时不可缺少的 `m_i`、`l_i` 和 `n_i`。

Direct Paged 到 Split-KV 从 `138.70/235.71/337.21` 提升为
`185.88/332.75/442.56 tok/s`，增加 34.0%/41.2%/31.2%。后续 Parallel Merge
又把 `310.95/637.37/985.26` 提升到 `314.69/675.49/996.56`；Profile 中 merge
kernel 时间下降 28.4%，c4 端到端提升 6.0%。

vLLM 的经典对应是 `paged_attention_v2_kernel`、
`paged_attention_v2_reduce_kernel`、`tmp_out`、`max_logits`、`exp_sums`；成熟
FlashAttention 后端也可通过 `num_splits` 选择 split-KV 路径。

## 9. 融合 Kernel：减少 launch 和中间 Tensor 往返

### 9.1 Fused Add + RMSNorm

优化前：

```python
residual = residual + hidden_states
variance = residual.float().pow(2).mean(dim=-1, keepdim=True)
hidden_states = weight * residual * torch.rsqrt(variance + eps)
```

Add 写出完整中间 Tensor，RMSNorm 随后再次读取并做归约。优化后：

```python
hidden_states, residual = fused_add_rms_norm(
    hidden_states,
    residual,
    weight,
    eps,
)
```

一个 kernel 完成向量化读取、相加、把未归一化结果保存为 residual、FP32 平方和
归约、`rsqrt`、乘权重和写回。Split-KV 后性能从
`185.88/332.75/442.56` 增至 `205.47/360.24/466.78 tok/s`，提升
10.5%/8.3%/5.5%。并发越高，Attention 占比越大，Norm 融合的相对收益越小。

vLLM 对应 `RMSNorm`、`torch.ops._C.fused_add_rms_norm` 和
`fused_add_rms_norm_kernel`。

### 9.2 Fused SiLU + Multiply：合理但没有稳定收益

优化前：

```python
gate, up = gate_up_projection.chunk(2, dim=-1)
hidden_states = F.silu(gate) * up
```

优化后：

```python
hidden_states = fused_silu_and_mul(gate_up_projection)
```

kernel 等价于：

```cpp
output[i] = silu(input[i]) * input[i + intermediate_size];
```

结果从 `205.47/360.24/466.78` 变为 `204.32/356.13/468.54 tok/s`，即
-0.6%/-1.1%/+0.4%，不构成稳定提升，最终默认关闭。原因是原生 PyTorch/Triton
路径在当前 shape 已足够高效，自定义 launch 和未充分特化的访存抵消了理论收益。

vLLM 有 `SiluAndMul` 与 `torch.ops._C.silu_and_mul`，但“vLLM 有”不能替代本机
A/B 数据。这个实验是整条优化链中最重要的反例之一。

### 9.3 Fused RoPE + Paged KV Write

优化前：

```python
query = query * cos + rotate_half(query) * sin
key = key * cos + rotate_half(key) * sin
paged_key_cache[slot_mapping] = key
paged_value_cache[slot_mapping] = value
```

旋转后的 Key 先写中间 Tensor，Cache 写 kernel 再读取。优化后：

```python
query = fused_rope_cache_write(
    query,
    key,
    value,
    positions,
    cos_sin_cache,
    slot_mapping,
    paged_key_cache,
    paged_value_cache,
)
```

同一 kernel 读取 cos/sin，旋转 Q/K，返回旋转后的 Q，并把旋转后的 K 与原始 V
直接写入物理 Cache slot。正式 A/B 测试关闭了无稳定收益的 Fused SiLU，基线是
Fused Add+RMSNorm 的 `205.47/360.24/466.78`。性能增至
`225.59/386.08/502.03 tok/s`，提升 9.79%/7.18%/7.55%。

vLLM 当前有 `RopeKVCacheFusionPass`、
`fused_rope_and_unified_kv_cache_update` 与
`csrc/libtorch_stable/cache_kernels_fused.cu`，设计目标直接对应。

### 9.4 GQA KV Tile Reuse

同一个 KV head 被一组 query heads 共享。未优化时，每个 query head 对应的 block
各自从全局显存读取相同 K/V tile：

```cpp
int kv_head = q_head / group_size;
load_kv_tile(key_cache, value_cache, kv_head, tile_id);
```

优化版让同组 query heads 在适合的 kernel 布局中复用同一 KV tile，减少重复全局
load。端到端从 `225.59/386.08/502.03` 增至
`229.04/394.45/509.26 tok/s`，提升 1.5%/2.2%/1.4%。收益较小是因为共享、同步和
寄存器压力也会增加，且整个模型不只由 Decode Attention 构成。

vLLM 的成熟 Attention kernel 同样理解 `num_q_heads/num_kv_heads` 的 GQA 分组，
通过专门 tile 布局避免 Python `repeat_interleave`；具体复用粒度依后端和 GPU
架构而定。

## 10. Prefill 专用路径：不要用 Decode 的形状假设处理长提示词

Decode 通常是“每请求 1 个 query、很长的历史 KV”，而 Prefill 是“每请求很多
query、Q/K 长度接近”。两者的最优 grid、访存方式和融合边界不同。只优化 Decode
会导致长提示词仍由 Mask 构造、小 kernel 和逐请求 Cache 写入主导。

### 10.1 无 Padding 的 Causal SDPA 快路径

优化前为了兼容不同 prompt 长度，总是创建 padding 与 causal 组合 Mask：

```python
token_positions = torch.arange(sequence_length, device=device)
causal = token_positions[None, :] <= token_positions[:, None]
valid_keys = token_positions[None, :] < prompt_lens[:, None]
attention_mask = causal & valid_keys[:, None, :]

attention = F.scaled_dot_product_attention(
    query,
    key,
    value,
    attn_mask=attention_mask,
    enable_gqa=True,
)
```

基准中的 128 个提示词都被构造成等长 1000 token，没有 padding key。优化后直接
让 PyTorch 选择 causal fast path：

```python
if uniform_full_prompt:
    attention = F.scaled_dot_product_attention(
        query,
        key,
        value,
        attn_mask=None,
        dropout_p=0.0,
        is_causal=True,
        enable_gqa=True,
    )
else:
    attention = padded_varlen_path(...)
```

这不是针对固定并发“凑批”，而是对运行时已经满足的 shape 条件选择更适合的正确
算子。性能从 `229.04/394.45/509.26` 增至
`257.69/477.20/688.15 tok/s`，提升 12.5%/21.0%/35.1%。高并发下每轮 Prefill
包含更多 token，因此取消二次 Mask 和允许高效 causal backend 的收益更明显。

vLLM 对应 Varlen FlashAttention Prefill，通过 `cu_seqlens_q/k` 表示变长边界，
等长只是其中一种合法输入，不依赖 dense padding Mask。

### 10.2 逐请求 Cache 写入到 Vectorized `index_copy_`

优化前：

```python
for batch_index in range(batch_size):
    positions = torch.arange(prompt_lens[batch_index], device=device)
    target = cache.slot_mapping(cache_slot, positions)
    key_cache.index_copy_(0, target, key[batch_index])
    value_cache.index_copy_(0, target, value[batch_index])
```

优化后在等长 Prefill 中一次生成所有目标 slot：

```python
positions = torch.arange(sequence_length, device=device)
target = cache.slot_mapping(
    cache_slots[:, None],
    positions[None, :],
).reshape(-1)

key_cache.index_copy_(
    0,
    target,
    key.transpose(1, 2).reshape(-1, num_kv_heads, head_dim),
)
value_cache.index_copy_(0, target, packed_value)
```

这减少 Python 循环和每请求 launch。吞吐从 `257.69/477.20/688.15` 提升到
`266.25/512.33/736.61 tok/s`，即 3.3%/7.4%/7.0%。变长路径仍只写有效 token，
没有为 padding 分配虚假 KV。

vLLM 的 `reshape_and_cache_flash` 更进一步：在自定义 kernel 中消费
`slot_mapping`，完成布局转换和 cache write。

### 10.3 Prefill Add+RMSNorm、RoPE+KV 与 Warp Reduction

Decode 上有效的融合继续扩展到 Prefill，但必须重新测试大 token shape。

Prefill Add+RMSNorm 从：

```python
residual = residual + hidden_states
hidden_states = rms_norm(residual, weight, eps)
```

改为：

```python
hidden_states, residual = fused_add_rms_norm(
    hidden_states,
    residual,
    weight,
    eps,
)
```

正式同轮 A/B 基线是自适应 SiLU 实验的 `262.39/498.83/717.67`，融合后为
`265.47/524.91/761.08 tok/s`，单项提升 1.18%/5.23%/6.05%；独立 Prefill
profile 中耗时下降 10.1%。若相对更早的 Vectorized KV 保留节点
`266.25/512.33/736.61`，累计变化则是 -0.3%/+2.5%/+3.3%，其中跨过了两轮 SiLU
试验，不能作为 RMSNorm 的单项归因。端到端的 MLP、Attention 和输出也会稀释
kernel 收益。

Fused Prefill RoPE+KV Write 把 QKV split、RoPE 和批量 slot 写入组合，profile
下降 3.2%；对应端到端快照为 `273.47/527.09/756.07 tok/s`。c8 相对上一快照
-0.7%，处于运行噪声范围，因此报告只把它记为“局部保留”，不宣称三档都加速。

RMSNorm 的 block reduction 随后改为 warp shuffle 加少量 shared memory：

```cpp
float local_sum = vectorized_square_sum(x);
float warp_sum = warp_reduce_sum(local_sum);

if (lane == 0) {
    warp_sums[warp_id] = warp_sum;
}
__syncthreads();

float block_sum = first_warp_reduce(warp_sums);
```

profile 中该 kernel 降低 1.84%；端到端快照为
`269.43/518.61/776.63 tok/s`。连续实验之间存在热状态差异，所以这个数字不能与
非相邻快照做严格加法归因。

## 11. 调度和输出：让 GPU 关键路径不再等待 Python

### 11.1 Pipelined Ignore-EOS 的收益和适用边界

优化前每步立即把 token 拉回 CPU 并判断结束条件：

```python
for request, token_tensor in zip(requests, sampled_tokens):
    token_id = int(token_tensor.item())
    request.append_decode_token(token_id)
    if token_id in eos_token_ids:
        request.finished = True
```

`.item()` 会形成 GPU 到 CPU 同步点。基准明确使用 `ignore_eos=true` 且固定生成
50 token，因此可以把当前 token 的 CPU 处理与下一次 replay 流水化：

```python
pending_output = sampled_token_ids
next_tokens = graph_manager.replay(next_inputs, positions, slots)
publish(pending_output)
```

吞吐从 `269.43/518.61/776.63` 提升至
`298.28/627.42/953.05 tok/s`，提高 10.7%/21.0%/22.7%（若与更早 RoPE
快照相比会得到更大的数字，不应重复累计）。

这项优化不适用于必须逐 token 及时识别 EOS、stop string 或复杂 logits processor
的所有在线请求。vLLM 有异步输出和减少同步点的同类目标，但不能声称 vLLM 使用
完全相同的 ignore-EOS 专用逻辑。

### 11.2 批量通知与为什么后来恢复逐 token 语义

逐 token、逐请求获取 Condition 并 `notify_all()` 会造成锁竞争：

```python
for request, token_id in outputs:
    with request.output_condition:
        request.decode_tokens.append(token_id)
        request.output_condition.notify_all()
```

批量版本一次更新多个 token 后再通知，性能达到
`310.95/637.37/985.26 tok/s`，相对 Pipelined 阶段提升 4.2%/1.6%/3.4%。但批量
交付会增加单 token ITL，且不能为了基准把多个 Decode step 藏在一次用户可见通知
里。项目随后建立“无等待、逐 token”正式基线：

```text
313.61 / 574.43 / 955.00 tok/s
```

c4/c8 的吞吐因此回落，c1 则在噪声内略高；这不是优化失败，而是主动删除两类
测试特化行为：等待凑批和四 token 聚合。后续所有系统优化都以请求到达即调度、
token 产生即交付为原则。

### 11.3 Continuous Batching V1/V2：不等待凑批也能提高占用

Run-to-completion 会让先到请求占住活动槽位直到生成完毕，新请求只能排队。V1
改为每个 step 重新接纳请求：

```python
token_budget = max_batch_num_tokens

for request in running_requests:
    schedule_decode_or_chunk(request, token_budget)

while waiting_requests and token_budget > 0:
    request = waiting_requests.popleft()
    schedule_prompt_chunk(request, token_budget)
```

V1 对无等待基线的变化为：

| 并发 | Run-to-completion | Continuous V1 | 变化 |
|---:|---:|---:|---:|
| 1 | 313.61 | 271.61 | -13.4% |
| 4 | 574.43 | 719.57 | +25.3% |
| 8 | 955.00 | 1063.06 | +11.3% |

它显著降低 c4/c8 的队头阻塞和 TTFT，但因为 Prefill 中临时 Tensor 脱离
`inference_mode` 生命周期，显存异常膨胀。V2 修正生命周期后为
`273.14/740.07/1061.22 tok/s`，c4 相对正式基线提升 28.8%，c8 提升 11.1%，
c1 则因 scheduler step 固定开销下降 12.9%。V2 被保留，因为它的资源行为正确，
且没有等待请求来制造 batch。

vLLM `Scheduler.schedule` 同样围绕 `token_budget`、`num_computed_tokens`、
`num_scheduled_tokens` 和 `KVCacheManager.allocate_slots` 工作。其源码明确没有永久
分离的 Prefill/Decode 阶段，而是每轮安排尚未计算的 token。

### 11.4 持久 Metadata、只重置 Padding 尾部和 Token Budget

每 step 新建 `input_ids/positions/cache_slots/block_table`，再对整个 Graph Buffer
清零，会产生很多 CPU 分配和 H2D 小拷贝。持久版本预分配最大容量：

```python
class PersistentStepBuffers:
    def __init__(self, capacity, max_blocks):
        self.input_ids = torch.empty(capacity, device="cuda")
        self.positions = torch.empty(capacity, device="cuda")
        self.cache_slots = torch.empty(capacity, device="cuda")
        self.block_table = torch.empty(
            capacity,
            max_blocks,
            dtype=torch.int32,
            device="cuda",
        )
```

运行时原地写有效前缀，并只重置上轮有效 batch 与本轮 batch 之间必要的 padding
尾部。持久 Metadata 从 Continuous V2 的 `273.14/740.07/1061.22` 提升至
`280.89/741.75/1103.82 tok/s`；尾部重置进一步变为
`280.72/753.45/1104.93 tok/s`，收益小但不依赖测试到达模式，因此保留。

把统一 token budget 固定为 2048 后得到 `281.26/734.18/1091.81 tok/s`：c4/c8
分别回退 2.56%/1.19%，但 c8 TTFT 明显降低。它作为与 vLLM 一致的容量和公平性
约束保留，不能记为吞吐优化成功。

### 11.5 异步 D2H 输出复制

优化前：

```python
sampled_token_ids = torch.argmax(logits, dim=-1)
token_ids = sampled_token_ids.cpu().tolist()
process_outputs(token_ids)
run_next_step()
```

优化后用独立 copy stream、pinned host buffer 和 Event：

```python
with torch.cuda.stream(output_copy_stream):
    output_copy_stream.wait_stream(torch.cuda.current_stream())
    pinned_token_ids.copy_(sampled_token_ids, non_blocking=True)
    ready_event.record(output_copy_stream)

output_queue.put((pinned_token_ids, ready_event, request_metadata))
```

输出线程等待 Event 后处理上一轮 token，而模型线程可以开始下一次 Graph replay。
相对 `202608150203` 正式基线，性能从 `280.72/753.45/1104.93` 提升到
`315.48/878.96/1268.37 tok/s`，提高 12.4%/16.7%/14.8%。c1 TTFT 增加
5.43 ms，来自 stream、snapshot 和 Event 固定成本；c8 TTFT 反而下降 18.97 ms。

vLLM 对应 `AsyncGPUModelRunnerOutput`、`async_output_copy_stream`、
`non_blocking=True` 和 CUDA Event。两者共同原则是把 D2H 和 Python 输出处理移出
下一轮 GPU 计算的关键路径。

## 12. 接入成熟 vLLM Kernel：明确复用边界

### 12.1 自写 Split-KV 到 Paged FlashAttention Decode

教学版 Attention 便于理解 page lookup、online softmax 与 split merge，但没有理由
假设一个项目内核能在短时间内超过长期维护的 FlashAttention。后期保留自研 Paged
Cache、调度器、Graph 和元数据，Attention 改为：

```python
attention = flash_attn_varlen_func(
    q=query,
    k=key_cache,
    v=value_cache,
    out=output,
    cu_seqlens_q=query_start_loc,
    seqused_k=sequence_lengths,
    block_table=block_table,
    max_seqlen_q=1,
    max_seqlen_k=max_model_len,
    causal=True,
)
```

性能从异步输出版的 `315.48/878.96/1268.37` 提升至
`363.65/982.74/1471.26 tok/s`，增加 15.3%/11.8%/16.0%；Profiler 中自写
Attention 相关总耗时下降 65.5%。

这一步必须准确表述为“自研执行器接入 vLLM/FlashAttention 的成熟 paged kernel”，
而不是“自研了一个更快的 FlashAttention”。自研价值在于此前逐步建立的 Cache
格式、Graph 静态 Buffer 和 Varlen 元数据能无缝满足该 kernel 的接口。

### 12.2 Mixed Prefill/Decode：单独有效，累计却回退

Mixed forward 允许一个 packed batch 同时包含：

```text
请求 A：1 个 Decode query
请求 B：1 个 Decode query
请求 C：一段 Prefill query
```

`query_start_loc`、`sequence_lengths`、`block_table` 保留请求边界。单独在
FlashAttention 基线上测试为 `361.22/982.61/1502.34 tok/s`，相对
`363.65/982.74/1471.26` 是 -0.7%/-0.0%/+2.1%。它更主要改善公平性和高并发
admission，不是纯 Decode 峰值。

但把 Mixed 与 vLLM fused ops 累计启用后，从
`381.00/1115.46/1685.51` 回退到 `372.46/1041.33/1569.10 tok/s`，下降
2.2%/6.7%/6.9%。原因是当时 mixed path 还未复用完整融合 residual 数据流，并
引入额外 packing 和 shape 处理。因此 Mixed 保留为实验开关，Qwen2 的最佳正式
基线不把这组负收益累计进去。

### 12.3 vLLM Fused RMSNorm 与 SwiGLU

自写融合 kernel 已证明方向正确，但 vLLM 算子对 dtype、向量宽度、shape 和架构做了
更成熟的特化。后期替换为：

```python
torch.ops._C.fused_add_rms_norm(
    hidden_states,
    residual,
    weight,
    eps,
)

silu_output = torch.empty(
    *gate_up_projection.shape[:-1],
    gate_up_projection.shape[-1] // 2,
    dtype=gate_up_projection.dtype,
    device=gate_up_projection.device,
)
torch.ops._C.silu_and_mul(silu_output, gate_up_projection)
hidden_states = silu_output
```

在同一个 Paged FlashAttention 基线上，从 `363.65/982.74/1471.26` 提升到
`381.00/1115.46/1685.51 tok/s`，提高 4.8%/13.5%/14.6%。三项 BF16 正确性测试
均通过 `atol=2e-2, rtol=2e-2`。

这也是为什么报告必须区分三种贡献：

1. 自己实现 kernel，理解并验证数学和布局；
2. 自研执行器完成固定 Cache、Graph、调度和接口集成；
3. 最终性能路径复用 vLLM/FlashAttention 的成熟 kernel。

把第 3 类全部称为“自研 CUDA 算子”会夸大结论。

### 12.4 Qwen2 高并发：Tokenizer、Detokenizer、预热和 Mixed Runner

c1/c4/c8 接近 GPU kernel 问题，高并发则会把网络事件循环、Tokenizer、输出文本
构造、Prefill admission 和 Python GIL 一并放大。项目因此继续做了以下同轮 A/B。

#### 异步 Tokenizer 与 Asyncio 输出队列

优化前在 Uvicorn 事件循环中直接执行同步 tokenizer：

```python
input_ids = tokenizer.apply_chat_template(messages)
scheduler.add_request(input_ids)
```

优化后把 CPU tokenizer 放到 worker，并通过异步队列将输出交回事件循环：

```python
input_ids = await asyncio.to_thread(
    tokenizer.apply_chat_template,
    messages,
)
await output_queue.put(engine_output)
```

Tokenizer 并不会让 GPU kernel 更快，价值是避免 HTTP 事件循环被 CPU 工作阻塞。
早期 `150126` 的数字仍依赖后来废止的等待/四 token 模式，因此只保留代码，不把
`304.24/911.30/1196.32` 计入正式累计曲线。

后期 Asyncio 输出队列在统一高并发基线上使 c16/c32 从约
`1819/2234` 提升到 `1973/2441 tok/s`，约 +8.4%/+9.3%；低并发略有回退，所以按
负载启用。vLLM 同样把 engine output 与 API server 的异步处理分层。

#### 全历史 Detokenize 到增量 Detokenize

初版批量输出处理器每到一个 token 都重新解码全部已生成 token：

```python
text = tokenizer.decode(request.output_token_ids)
```

生成 `D` 个 token 会处理 `1+2+...+D=O(D²)` 个 token。增量版本只处理新增后缀并
维护 decoder state：

```python
new_text, state = incremental_detokenizer.append(
    new_token_ids,
    request.detokenizer_state,
)
```

这让批量输出处理器从负优化变成有效路径；同轮 c16/c32 从
`2009.00/2485.76` 提升到 `2155.08/2536.63 tok/s`。vLLM 的 output processor
同样维护增量 token/text 状态，不会每步重做完整 decode。

#### 最大 Token Budget 预热与跳过必然丢弃的 Replay

只用单 token 假请求预热不能覆盖大 Prefill 的 GEMM heuristic、allocator workspace
和 kernel lazy load。优化后启动时构造一次满足 `max_num_batched_tokens=2048` 的
假请求：

```python
warmup_prompt = torch.full(
    (max_num_batched_tokens,),
    pad_token_id,
    device=device,
)
model.prefill(warmup_prompt, warmup_metadata)
torch.cuda.synchronize()
```

结果 c16/c32 从 `1835.41/2402.19` 提升到
`1949.11/2439.27 tok/s`，即 +6.2%/+1.5%。这不是把预热时间从 benchmark 中
“作弊删除”，而是服务启动阶段显式完成所有生产服务都会经历的一次性初始化；报告
仍分别记录启动和模型加载后基线。

固定输出 50 token 时，旧流水线会为刚完成请求再 replay 一次，其结果必然丢弃。
加入 terminal mask 后跳过这次第 51 步：

```python
if all(request.will_finish_after_pending_token for request in requests):
    publish_pending_tokens()
else:
    replay_next_decode_graph()
```

同轮 `1949.11/2439.27 → 1954.60/2434.27 tok/s`，变化在噪声范围，但删除的是
确定无用计算，所以保留。

#### 统一 Mixed Runner、vLLM RMSNorm 与 Fused RoPE

“Prefill eager forward + Decode Graph forward”交替不能共享同一批 GEMM，还会频繁
切换 metadata。统一 packed mixed runner 后，先接入成熟 RMSNorm：

```python
hidden_states, residual = vllm_fused_add_rms_norm(...)
hidden_states = layer.mixed(
    hidden_states,
    query_start_loc,
    sequence_lengths,
    block_table,
)
```

同轮 c16/c32 从 `1954.60/2434.27` 提升到
`2192.30/2544.37 tok/s`，增加 12.2%/4.5%。再把 Mixed Q/K RoPE 与 Paged Cache
写入融合：

```python
query = fused_rope_cache_write(
    query,
    key,
    value,
    positions,
    slot_mapping,
    key_cache,
    value_cache,
)
```

得到最终 Qwen2 c16/c32 `2254.40/2546.50 tok/s`。同轮 vLLM 是
`2414.44/5720.15`，即 93.4%/44.5%。c32 的巨大差距说明：自研 Decode Graph
单步已经接近 vLLM，并不代表整个持续服务 runner 已经接近；Prefill admission、
Python metadata、输出与活动 batch 保持能力仍会让 GPU 出现空洞。

## 13. Qwen3.5-4B：从“能加载”到 Hybrid 专用执行器

### 13.1 为什么不能只换模型路径

Qwen2 是每层全注意力；Qwen3.5-4B text backbone 包含 32 层，其中 8 层是 full
attention，24 层是 Gated DeltaNet linear attention。后者不保存完整历史 K/V，
而是维护短卷积状态和 recurrent/SSM state。把 32 层都当 Qwen2 Attention 会得到
错误模型；把 state 存成逐请求 Python Tensor 又会在高并发下产生大量 stack、clone
和小 kernel。

为建立严格起点，`qwen3_5_demo.py` 只增加模型必需结构，不带入后期性能能力。它会
在每层从请求字典收集状态：

```python
conv_states = torch.stack(per_request_conv_states)
recurrent_states = torch.stack(per_request_recurrent_states)
```

计算后再逐请求复制回去：

```python
for index, request in enumerate(requests):
    request_cache[CONV][layer_index] = conv_states[index].clone()
    request_cache[RECURRENT][layer_index] = final_state[index].clone()
```

这版真实加载 426 个文本权重，能正确运行 1 至 16 并发，但性能只有
`20.05/34.01/53.05/70.95/6.46 tok/s`。c16 的显存利用率超过 97%，功耗反而下降，
说明时间消耗在状态搬运、allocator 和小 kernel，而不是高效矩阵计算。c32 八分钟只
完成 6/128 请求，因此停止；c64 未启动。

### 13.2 Hybrid Cache：两类层使用两类状态

优化版先按 `config.layer_types` 建立层映射：

```python
full_layer_indices = tuple(
    i for i, layer_type in enumerate(config.layer_types)
    if layer_type == "full_attention"
)
linear_layer_indices = tuple(
    i for i, layer_type in enumerate(config.layer_types)
    if layer_type == "linear_attention"
)
```

Cache 结构为：

```text
8 个 Full Attention 层
    Paged Key Cache  [layer, page, page_offset, kv_head, head_dim]
    Paged Value Cache
    Block Table / Slot Mapping

24 个 Gated DeltaNet 层
    Conv State       [layer, request_slot, conv_dim, kernel_size-1]
    Recurrent State  [layer, request_slot, value_head, value_dim, key_dim]
```

Recurrent state 使用模型/内核所需的 FP32 累积精度。所有状态在启动时预分配，
请求只持有 `request_slot`；请求结束归还 slot，而不是为每一步 stack/clone 新 Tensor。
Full-attention 部分为每个 real/null slot 固定预留
`ceil(max_model_len/block_size)` 个 Page，并非按请求实际长度从 free list 取 Block。
这是当前 Hybrid 教学实现为简化 Graph 采用的容量权衡，不等同于 vLLM 动态 BlockPool。

### 13.3 Prefill 与 Decode 使用不同 GDN kernel

Packed Prefill 路径：

```python
mixed_qkv = causal_conv1d_fn(
    mixed_qkv.transpose(0, 1),
    conv_weight,
    conv_states=cache.conv_states[layer],
    query_start_loc=query_start_loc,
    cache_indices=state_indices,
    has_initial_state=has_initial_state,
    activation="silu",
).transpose(0, 1)

output, final_state = chunk_gated_delta_rule(
    q=query,
    k=key,
    v=value,
    initial_state=initial_state,
    cu_seqlens=query_start_loc,
    output_final_state=True,
    use_qk_l2norm_in_kernel=True,
)

cache.recurrent_states[layer].index_copy_(
    0,
    request_cache_slots,
    final_state,
)
```

单 token Decode 路径使用原地状态更新：

```python
mixed_qkv = causal_conv1d_update(
    mixed_qkv,
    cache.conv_states[layer],
    conv_weight,
    conv_state_indices=state_indices,
    activation="silu",
)

fused_recurrent_gated_delta_rule_packed_decode(
    mixed_qkv=mixed_qkv,
    initial_state=cache.recurrent_states[layer],
    ssm_state_indices=state_indices,
    out=output,
    use_qk_l2norm_in_kernel=True,
)
```

这样 Prefill 使用适合长序列的 chunk parallel delta rule，Decode 使用适合单 token
的 recurrent update，不再让一个通用 Python 公式兼顾两种完全不同的 shape。

vLLM 的对应实现位于 `vllm/model_executor/models/qwen3_5.py` 与
`vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py`，包括
`Qwen3_5DecoderLayer`、`QwenGatedDeltaNetAttention`、
`causal_conv1d_update` 和
`fused_recurrent_gated_delta_rule_packed_decode`。

### 13.4 层级分流与融合 residual 数据流

每层根据类型调用 full attention 或 GDN：

```python
if self.layer_type == "full_attention":
    hidden_states = self.self_attn.forward_packed(...)
else:
    hidden_states = self.linear_attn.forward_packed(...)
```

层前、Attention/GDN 后继续携带融合 residual：

```python
hidden_states, residual = vllm_fused_add_rms_norm(
    hidden_states,
    residual,
    input_layernorm_weight,
    eps,
)

hidden_states = attention_or_gdn(hidden_states)

hidden_states, residual = vllm_fused_add_rms_norm(
    hidden_states,
    residual,
    post_attention_layernorm_weight,
    eps,
)
```

Full Attention 层复用 Paged FlashAttention，整个 Decode 路径再按固定 batch bucket
捕获 CUDA Graph。最终性能为：

|---:|---:|---:|---:|---:|
| 1 | 20.05 | 61.90 | 62.91 | 98.4% |
| 2 | 34.01 | 106.13 | 112.11 | 94.7% |
| 4 | 53.05 | 173.33 | 180.43 | 96.1% |
| 8 | 70.95 | 253.99 | 267.95 | 94.8% |

4. 真正稳定的大收益来自命中关键路径：Continuous Batching、异步 D2H、成熟

| Slot 写入 | `slot_mapping`、`fused_rope_cache_write` | `FlashAttentionImpl.do_kv_cache_update`、`reshape_and_cache_flash` | 都将新 K/V 写入固定物理 slot |

| Split-KV | `paged_gqa_decode_split*` 与 merge kernel | `paged_attention_v2_kernel`、`paged_attention_v2_reduce_kernel`、`num_splits` | 都保存局部 max/sum/numerator 后稳定合并 |
| CUDA Graph bucket | `FixedBatchCUDAGraph`、`CUDAGraphBatchManager` | `vllm/v1/cudagraph_dispatcher.py::CudagraphDispatcher`、`compilation/cuda_graph.py::CUDAGraphWrapper` | 固定 Buffer 地址，按 batch bucket 捕获并 padding replay |
| Add+RMSNorm | `cuda_attention/fused_rms_norm.cu` | `model_executor/layers/layernorm.py::RMSNorm`、`torch.ops._C.fused_add_rms_norm` | 教学 kernel 验证方向；最终使用 vLLM 成熟算子 |
| SwiGLU | `cuda_attention/fused_silu_mul.cu` | `model_executor/layers/activation.py::SiluAndMul` | 自写版本无稳定收益；最终使用成熟实现 |
| RoPE+Cache Write | `cuda_attention/fused_rope_cache_write.cu` | `compilation/passes/fusion/rope_kvcache_fusion.py::RopeKVCacheFusionPass` | 都减少旋转后 K 的中间落地，具体调用边界不同 |
| Async D2H | `v3_openai_server.py` 的 copy stream/Event | `vllm/v1/worker/gpu_model_runner.py::AsyncGPUModelRunnerOutput` | 都用 pinned host buffer、非阻塞复制和 Event 重叠下一 step |
| Mixed Prefill/Decode | `Qwen2ForCausalLMGraph.mixed`、server mixed admission | v1 scheduler + varlen backend | 目标一致；本项目早期 mixed 的 Python packing 曾造成回退 |
| Qwen3.5 层分流 | `qwen3_5_demo_v1.py::Qwen3_5DecoderLayer` | `model_executor/models/qwen3_5.py::Qwen3_5DecoderLayer` | 都按 `config.layer_types` 分流 full/linear attention |
| GDN Prefill/Decode | `Qwen3_5GatedDeltaNet.forward_packed/forward_decode` | `layers/mamba/gdn/qwen_gdn_linear_attn.py` | 本项目直接复用 causal-conv 与 Delta Rule 核心算子并自行集成 Cache/Graph |

映射表不表示两套系统已经完全相同。尤其后期的 FlashAttention、RMSNorm、SwiGLU
和 GDN 核心算子来自当前 vLLM 环境；本项目的贡献是从教学公式逐步建立可兼容这些
算子的布局、Cache、Graph、调度器和服务流水线，并通过 A/B 说明每层抽象为何存在。

## 16. 为什么最终能达到 vLLM 的 90% 以上

### 16.1 不是一个 kernel，而是逐层消除不同种类的浪费

| 浪费类型 | 最初表现 | 最终处理方式 |
|---|---|---|
| 历史网络重算 | 每个 Decode token 重跑完整序列 | 逐层 KV Cache / GDN recurrent state |
| GQA 冗余 | 2 个 KV heads 显式复制为 14 个 | kernel 内 `q_head → kv_head` 映射 |
| 跨请求 Attention | 全局 dense Q×K 和大 Mask | Packed Varlen 边界、有效 tile、Paged FlashAttention |
| Cache 搬运 | 每步 `torch.cat` 或 `index_select` gather | 固定 Paged Cache、Direct Paged read |
| 长 KV 串行 | 一个 CTA 扫完整历史 | Split-KV partitions + 稳定并行 merge |
| Kernel launch | 每 token 重新提交整模型 | batch bucket CUDA Graph replay |
| 中间显存往返 | Add/Norm、RoPE/Cache、SiLU/Mul 分离 | 经 A/B 选择有效融合，最终复用成熟 fused ops |
| CPU/GPU 同步 | `.item()`、同步 D2H、逐请求通知 | copy stream、pinned buffer、Event、增量输出 |
| 队头阻塞 | 请求 run-to-completion | 无等待 Continuous Batching 与 token budget |
| Qwen3.5 状态搬运 | 每层 stack/clone 逐请求 GDN state | 固定 Hybrid state slots 和专用 Prefill/Decode kernel |

这些问题位于不同层次，不能互相替代。例如 CUDA Graph 不会消除跨请求 Q/K，Paged
KV 不会自动使 Attention 直接读 page，Fused RMSNorm 也不会修复 Python 输出同步。
最终接近 vLLM 是这些层共同成立后的结果。

### 16.2 两段加速曲线必须分开解释

Qwen2 CUDA 从早期 `50.04/87.68/83.69` 到后期
`381.00/1115.46/1685.51 tok/s`，时间线倍率为 7.61x/12.72x/20.14x。由于部分
中间报告是从共同基线做的隔离实验，这个倍率只比较首尾，不能把每行百分比连乘。

Qwen3.5-4B 则从“只有模型必需结构”的
`20.05/34.01/53.05/70.95 tok/s` 提升到
`61.90/106.13/173.33/253.99 tok/s`，为 3.09x/3.12x/3.27x/3.58x。它不是把
Qwen2 吞吐迁移到 4B 模型，而是复用此前已验证的执行器能力，再为 24 个 GDN 层
增加正确的固定状态 Cache 和专用 kernel。

### 16.3 “90%+”成立的具体原因

最终 Qwen3.5 与 vLLM 使用相同模型、dtype、请求数、输入/输出长度、上下文上限和
活动序列上限；自研执行器又复用了相同环境中的成熟 FlashAttention、fused ops 与
GDN 核心算子。因此最大计算热点已经非常接近。剩余差异主要落在 runner、状态索引、
调度和输出，而不是矩阵公式。

在同轮七档测试中：

```text
c1   61.90 / 62.91 = 98.4%
c2  106.13 / 112.11 = 94.7%
c4  173.33 / 180.43 = 96.1%
c8  253.99 / 267.95 = 94.8%
c16 327.26 / 350.22 = 93.4%
c32 363.71 / 391.44 = 92.9%
c64 361.35 / 393.53 = 91.8%
```

七档简单平均约 94.6%，最低值 91.8%，所以“达到 vLLM 90% 以上”成立。它不是
“完全自写所有 CUDA kernel 后达到 90%”，而是“自研教学执行器经过布局、Cache、
Graph、调度和模型专用集成后，在最终性能路径复用成熟核心算子，达到完整 vLLM
服务的 91.8% 至 98.4%”。

### 16.4 为什么 Qwen2 c32 很差，Qwen3.5 c32 却超过 90%

这两个结果不矛盾，也不能直接相减：

- Qwen2-0.5B 单层计算很短，Python/launch/admission 的固定开销占比极高；当时的
  mixed runner 和输出链尚未完成，高并发 GPU 更容易出现空洞。
- Qwen3.5-4B 计算更重，固定 CPU 开销被更大的 GEMM/GDN 工作摊薄。
- Qwen3.5 只有 8 个 full-attention 层；其余 24 层 Decode 使用固定大小 recurrent
  state，而不是随历史增长读取 KV。
- 最终 Qwen3.5 路径已经包含更晚完成的异步输出、增量 Detokenize、统一 mixed
  runner、固定 Hybrid Cache 和 GDN 专用算子。

因此 Qwen3.5 的 90% 结果证明最终 Hybrid 路径有效，不应反向改写成 Qwen2 c32
也曾达到 90%。

## 17. 尚未与 vLLM 完全一致的部分

1. **静态 Slot 容量**：最终 Graph/Hybrid 路径尚未接回动态 BlockPool；一个短请求
   占用 slot 期间也锁定 `max_model_len` 对应 Page 容量，vLLM 可把未用 Block 分给
   其他请求。
2. **GDN Prefill 状态搬运**：当前仍有 `index_select/index_copy_`；vLLM 的 packed
   state 管理与 kernel 集成更深入。
3. **融合边界**：Q/K norm、partial RoPE、Cache write、GDN gate/state update
   仍有可合并的独立操作。
4. **持久 GPU runner**：自研服务仍有更多 Python 请求对象、metadata 构造和
   active-set 管理；vLLM 的 scheduler/runner/block manager 更成熟。
5. **输出能力**：本次主要验证固定长度 greedy text generation；复杂 sampling、
   stop strings、structured output、speculative decoding 会增加不同热路径。
6. **模型范围**：当前 Qwen3.5 只覆盖 text-only；视觉输入、MTP、分布式并行、量化
   和多 LoRA 不在本次 90% 结论内。
7. **测试范围**：单机单卡、固定 1000+50、请求率无穷大不能代表所有线上长度分布。

最终自研显存约比 vLLM 少 1 GiB、主机内存少约 2.5 GiB；vLLM 用更多 Cache 与
runtime workspace 换取略高的高并发吞吐。显存更少本身不是胜负指标，需要与容量、
TTFT、TPOT 和吞吐一起判断。

## 19. 最终结论

从 `qwen2_demo.py` 出发，最关键的学习不是记住某个 kernel 名，而是建立一条可验证
的性能推理链：先确认数学正确，再用同轮 A/B 找到真正瓶颈；一次只改变一个方向；
负优化立即记录并恢复；最后才把已经理解的数据布局接到成熟实现上。

项目最终接近 vLLM，不是靠等待凑批、放宽口径或隐藏失败实验，而是依次解决了历史
重算、跨请求无效计算、Cache 搬运、长 KV 串行、kernel launch、显存往返、CPU/GPU
同步、队头阻塞和 Qwen3.5 GDN 状态管理。严格结论是：在本报告规定的 Qwen3.5-4B
单卡文本基准中，自研执行器达到 vLLM 的 91.8% 至 98.4%；在该范围之外仍需重新
测试，不能自动外推。
