# v2-0807 性能测试

## 1. 测试结论

本次使用当前 v2 代码重新加载模型，测试 1、2、4 并发。三组均为 10/10
请求成功，实际处理 10000 个输入 token 和 100 个输出 token。

当前结果如下：

- 1 并发：总耗时 20.54 秒，输出吞吐量 4.867 token/s。
- 2 并发：总耗时 40.13 秒，输出吞吐量 2.492 token/s。
- 4 并发：总耗时 53.29 秒，输出吞吐量 1.876 token/s。

当前实现可以正确执行 Prefill/Decode 混合调度，但并发数增加后吞吐量下降。
原因是多个请求被拼接到普通 PyTorch SDPA 的全局 Attention 矩阵中，Mask 只能
屏蔽跨请求结果，不能避免对应的矩阵计算。当前实现还不是 vLLM 的高效
Continuous Batching kernel。

## 8. 当前版本限制

1. `max_num_seqs=4` 允许多请求进入同一轮，但普通 SDPA 仍会构造完整的全局
   Attention 矩阵，Mask 不会消除跨请求矩阵乘法成本。
2. `max_batch_num_tokens=4000` 会将多个 1000-token Prefill 合并成大矩阵，在
   MPS 上不一定比小 batch 更快。
3. Attention Mask 使用普通 PyTorch 张量，尚未使用 vLLM 的变长 Attention kernel。
4. KV Cache 仍是教学实现，不是 Paged KV Cache；Cache 回收、取消请求和异常
   清理尚未完善。
5. benchmark 设置 `temperature=0`，但当前采样函数仍在 Top-K 候选中使用
   `torch.multinomial`，因此生成文本不保证严格复现。

## 12. 本版本实现重点：Chunked Prefill 和 Continuous Batching

本版本的主要目标不是只完成单请求 Decode，而是演示多个请求在同一个 Scheduler
中交错执行。核心实现包括 Chunked Prefill、Continuous Batching、逐请求 KV
Cache，以及扁平 token 输入。

### 12.1 Chunked Prefill

Chunked Prefill 将一个很长的输入拆成多个小块，每轮只处理当前请求的一部分
Prefill token，而不是一次处理完整输入。

`Request` 使用以下状态描述当前处理进度：

| 状态 | 含义 |
|---|---|
| `prefill_seq_len` | 请求原始输入的总 token 数 |
| `start` | 本轮输入在请求序列中的起始位置 |
| `position` | 本轮输入在请求序列中的结束位置 |
| `decode_tokens` | 已经生成的 token 列表 |

每次 Scheduler 调用 `step()` 时，会通过：

```python
get_next_process_len(chunk_prefill_tokens)
get_and_set_next_process(chunk_prefill_tokens)
```

计算当前请求本轮应该处理的 token 数，并更新 `start` 和 `position`。例如，
输入长度为 1000、`chunk_prefill_tokens=250` 时，Prefill 可能按下面的方式执行：

```text
第 1 轮：[0:250]
第 2 轮：[250:500]
第 3 轮：[500:750]
第 4 轮：[750:1000]
```

Prefill 完成后，请求进入 Decode，每轮只取一个新 token：

```text
[1000:1001]
[1001:1002]
[1002:1003]
```

Scheduler 同时使用 `max_batch_num_tokens` 限制一轮中所有请求的 Query token
总数，避免一个超长请求占满整个模型前向。

### 12.2 Continuous Batching

本版本的 Continuous Batching 由三个队列和一个后台 Scheduler 线程组成：

| 队列 | 作用 |
|---|---|
| `waiting_list` | 已提交但尚未进入当前计算批次的请求 |
| `running_list` | 当前 Scheduler 正在持续处理的请求 |
| `finished_list` | 已生成结束的请求 |

网络线程调用 `Scheduler.add_request()` 时，请求先进入线程安全的
`incoming_requests` 队列。后台线程每轮执行以下流程：

```text
接收新请求
    -> 加入 waiting_list
    -> 为 running 请求安排下一段 Prefill 或一个 Decode token
    -> 在 token 预算允许时加入新的 waiting 请求
    -> 把所有当前 token 扁平化
    -> 执行一次模型前向
    -> 保存 KV Cache 并生成下一个 token
    -> 移除已完成请求
    -> 进入下一轮
```

因此，一个请求正在 Decode 时，新的请求可以加入下一轮 Prefill；不需要等待
所有旧请求完全结束后才接受新请求。这就是本 demo 中“连续”的含义。

### 12.3 混合 Prefill/Decode 批次

模型前向不再接收传统的 `[B, S, H]`，而是接收扁平的：

```text
hidden_states: [S_total, hidden_size]
```

`S_total` 是本轮所有请求当前 Query token 数的总和。Scheduler 同时生成
`query_start_loc`，记录每个请求在扁平 Query 中的边界：

```text
请求 1：4 个 token
请求 2：2 个 token
请求 3：1 个 token

query_start_loc = [0, 4, 6, 7]
input_ids.shape = [7]
```

在混合调度中可能出现：

```text
query_start_loc = [0, 1, 251, 501, 751]
```

它表示：

- 请求 1：1 个 Decode token
- 请求 2：250 个 Prefill token
- 请求 3：250 个 Prefill token
- 请求 4：250 个 Prefill token

Attention 根据这些边界分别读取各请求的 KV Cache，并使用请求内部的因果
Mask，防止一个请求访问另一个请求的 Key/Value。LM Head 再根据每个请求的
Query 边界选择该请求最后一个 Query 的 logits，用于生成下一个 token。

### 12.4 KV Cache 在连续批处理中的作用

每个请求、每个 Transformer 层分别保存 Key/Value：

```text
kv_cache_manager[request_id][KVCacheType.K][layer_index]
kv_cache_manager[request_id][KVCacheType.V][layer_index]
```

Prefill 阶段会把当前块的 Key/Value 追加到该请求的 Cache；Decode 阶段只追加
一个新 token 的 Key/Value。下一轮 Decode 不需要重新计算完整的输入序列。

这使得不同请求可以处于不同阶段：

```text
请求 1：Decode，已有 1000 个历史 KV
请求 2：Prefill，当前处理第 501--750 个 token
请求 3：Decode，已有 300 个历史 KV
```

它们仍然可以在同一个模型前向中处理。

### 12.5 与 vLLM 原生实现的差异

本版本用于学习调度原理，和 vLLM 原生实现仍有明显差异：

1. 当前使用 Python 循环拆分请求，并使用普通 PyTorch SDPA。
2. Attention Mask 是一个扁平的 dense mask；被屏蔽的跨请求矩阵区域仍可能被算子计算。
3. KV Cache 不是 Paged KV Cache，Cache block 分配和回收还不完善。
4. Scheduler 的请求取消、异常回收、抢占和严格的 token 预算管理仍是简化版本。
5. vLLM 使用专门的变长 Attention kernel 和 paged KV Cache，能够避免本 demo
   中全局 dense Attention 带来的跨请求计算浪费。

因此，当前版本已经实现了 Chunked Prefill 和 Continuous Batching 的基本控制
流程，但 4 并发下吞吐下降是当前 dense Attention 实现的预期限制，不代表
vLLM 原生 Continuous Batching 的性能表现。
