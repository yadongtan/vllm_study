# v0-0806 性能测试

## 1. 测试结论

v0 在 Apple M4 的 MPS 设备上可以通过 OpenAI 兼容接口稳定完成标准
`vllm bench serve` 测试。1 并发和 4 并发均为 10/10 请求成功，实际输入、
输出 token 数也完全符合测试配置。

4 并发没有提高总吞吐量：两组的输出吞吐量均约为 1.45 token/s，总耗时均约
为 69 秒。4 并发平均 TTFT 从 704.50 ms 增加到 17173.25 ms，说明请求主要
消耗在等待单请求推理锁，而不是被合并成批次执行。

这是符合 v0 设计预期的结果。v0 没有 KV Cache、连续批处理或调度器，每生成
一个 token 都会重新计算“1000 输入 token + 已生成 token”的完整序列。

- TTFT：Time To First Token，从请求发出到收到第一个输出 token。

- 总 token 吞吐量包含输入 token，因此不能直接代表生成速度。

## 6. 结果分析

### 6.1 1 并发

单请求平均占用的整体墙钟时间约为 `68.94 / 10 = 6.89 s`。首 token 需要
完成 1000-token Prefill，平均耗时约 0.70 秒；之后每个输出 token 又重新计算
完整序列，所以 TPOT 约为 0.69 秒。

### 6.2 4 并发

总耗时和输出吞吐量相对 1 并发几乎没有变化，证明 v0 没有利用并发请求形成
批量推理。服务器可以同时维持 4 个 HTTP/SSE 连接，但 MPS 模型执行受全局锁
保护，一个请求生成完 10 个 token 后，下一个请求才能进入模型。

4 并发的平均 TTFT 是 1 并发的约 24.4 倍。TPOT 和 ITL 基本不变，因为请求
一旦取得推理锁，其逐 token 执行速度与单并发相同。

### 6.3 v0 的主要瓶颈

1. 没有 KV Cache，每个输出 token 都重复计算约 1000 个历史 token。
2. 没有连续批处理，多个请求不能在同一次模型前向中共同执行。
3. 推理锁覆盖一个请求的完整生成周期，并发请求只能排队。
4. 教学实现使用普通 PyTorch SDPA，没有使用 vLLM 的 Paged Attention 和后端
   优化算子。

## 8. 复现命令

启动 v0 Web Server：

```bash
.venv/bin/python study/v0_openai_server.py --port 8000
```

1 并发：

```bash
.venv/bin/vllm bench serve \
  --backend openai \
  --base-url http://127.0.0.1:8000 \
  --endpoint /v1/completions \
  --model qwen2-0.5b-instruct-v0 \
  --tokenizer models/Qwen/Qwen2-0.5B-Instruct \
  --dataset-name random \
  --random-input-len 1000 \
  --random-output-len 10 \
  --random-range-ratio 0 \
  --num-prompts 10 \
  --max-concurrency 1 \
  --request-rate inf \
  --ignore-eos \
  --temperature 0
```

4 并发使用相同命令，只需改为：

```bash
--max-concurrency 4
```

## 9. v1 优化方向

下一版本首先应实现逐层 KV Cache，把 Decode 阶段从“重复处理整个历史序列”
改为“每层只处理一个新 token”。在此基础上，再增加等待队列和连续批处理，
将不同请求当前轮的 token 合并成一个 batch。完成后应使用本文完全相同的参数
重新测试，重点比较输出吞吐量、TTFT 和 4 并发相对 1 并发的扩展能力。
