# v1-0806 性能测试

## 1. 测试结论

v1 在 Apple M4 的 MPS 设备上可以通过 OpenAI 兼容接口稳定完成标准
`vllm bench serve` 测试。1 并发和 4 并发均为 10/10 请求成功，实际输入、
输出 token 数也完全符合测试配置。

相较 v0，v1 的主要收益来自逐层 KV Cache。1 并发平均 TPOT 从 687.60 ms
下降到 114.47 ms，降低 83.35%；输出吞吐量从 1.45 token/s 提升到
3.17 token/s，提高 118.76%；总耗时从 68.94 秒缩短到 31.51 秒。

当前版本仍按完整请求持有全局推理锁，没有连续批处理。4 并发没有带来吞吐
扩展：输出吞吐量为 2.47 token/s，反而低于 1 并发的 3.17 token/s；平均
TTFT 从 2119.66 ms 增加到 12887.51 ms，主要时间仍消耗在请求排队。

本次已将 `max_prefill_chunk_tokens` 恢复为 1000。测试 prompt 恰好为 1000
token，因此每个请求只执行一次 prefill，不再产生 10-token 小块导致的 100 次
前向调用开销。

## 6. 与 v0 对比

### 6.1 1 并发

| 指标 | v0 | v1 | 变化 |
|---|---:|---:|---:|
| 总耗时 | 68.94 s | 31.51 s | -54.29% |
| 请求吞吐量 | 0.1451 req/s | 0.3173 req/s | +118.76% |
| 输出吞吐量 | 1.4506 token/s | 3.1734 token/s | +118.76% |
| 平均 TTFT | 704.50 ms | 2119.66 ms | +200.87% |
| 平均 TPOT | 687.60 ms | 114.47 ms | -83.35% |
| 平均 ITL | 618.84 ms | 103.02 ms | -83.35% |

KV Cache 把 decode 从“每步重新处理约 1000 个历史 token”改为“每层只处理
一个新 token”，因此 TPOT 和 ITL 约降至 v0 的六分之一。虽然 v1 的首 token
延迟高于本次引用的 v0 基线，但后续 9 个 token 的节省更大，单请求整体时间
仍缩短 54.29%。

### 6.2 4 并发

| 指标 | v0 | v1 | 变化 |
|---|---:|---:|---:|
| 总耗时 | 69.01 s | 40.41 s | -41.44% |
| 请求吞吐量 | 0.1449 req/s | 0.2474 req/s | +70.76% |
| 输出吞吐量 | 1.4491 token/s | 2.4745 token/s | +70.76% |
| 平均 TTFT | 17173.25 ms | 12887.51 ms | -24.96% |
| 平均 TPOT | 688.91 ms | 117.27 ms | -82.98% |
| 平均 ITL | 620.02 ms | 105.54 ms | -82.98% |

4 并发下 v1 同样显著降低 decode 延迟。由于单个请求更快释放推理锁，平均
TTFT 相比 v0 降低 24.96%。但请求仍然串行执行，4 并发 v1 相对 1 并发 v1
的总耗时增加 28.24%，输出吞吐下降 22.02%，没有并发扩展能力。

## 7. 结果分析

### 7.1 KV Cache 收益

v0 的每个输出 token 都需要重新处理完整 prompt 和此前生成 token。v1 在一次
prefill 后保存每层 Key/Value，decode 只输入最后生成的一个 token。测试结果中
TPOT 从约 688 ms 降到约 115 ms，证明 KV Cache 已实际生效。

### 7.2 Prefill 表现

1000-token prompt 使用一个 1000-token chunk 完成 prefill，避免了小 chunk
反复启动 MPS 算子的开销。不过，本次 1 并发平均 TTFT 为 2119.66 ms，高于
v0 的 704.50 ms。后续应单独测量模型 prefill 前向时间，并分析 Cache 写入、
显式 GQA KV 复制以及 MPS 内存操作的成本。

### 7.3 并发瓶颈

v1 服务端仍用全局 `inference_lock` 包住一个请求的完整生成过程。并发请求只能
同时保持 HTTP/SSE 连接，不能合并为模型 batch。4 并发的 TPOT 与 1 并发接近，
但 TTFT 增加到约 12.89 秒，符合串行排队特征。

### 7.4 当前限制

1. 模型的 KV Cache 路径目前只支持 `batch_size=1`。
2. 没有等待队列调度和连续批处理。
3. GQA 的 Key/Value 在写入 Cache 前扩展到全部 Query heads，增加 Cache 内存。
4. 教学实现使用普通 PyTorch SDPA，没有 Paged Attention 和专用后端算子。

## 9. 复现命令

启动 v1 Web Server：

```bash
.venv/bin/python study/v1_openai_server.py --port 8001
```

1 并发：

```bash
.venv/bin/vllm bench serve \
  --backend openai \
  --base-url http://127.0.0.1:8001 \
  --endpoint /v1/completions \
  --model qwen2-0.5b-instruct-v1 \
  --tokenizer models/Qwen/Qwen2-0.5B-Instruct \
  --dataset-name random \
  --random-input-len 1000 \
  --random-output-len 10 \
  --random-range-ratio 0 \
  --num-prompts 10 \
  --max-concurrency 1 \
  --request-rate inf \
  --ignore-eos \
  --temperature 0 \
  --save-result \
  --save-detailed \
  --result-dir study/benchmark_results \
  --result-filename v1-0806-concurrency-1.json
```

4 并发使用相同命令，只需改为：

```bash
--max-concurrency 4 \
--result-filename v1-0806-concurrency-4.json
```

## 10. 下一步优化方向

下一版本应优先实现跨请求的连续批处理，使等待队列中的 prefill/decode token
能够进入同一次模型前向。随后应避免在 Cache 中保存重复扩展后的 GQA KV heads，
并分别增加纯 prefill、纯 decode 和端到端 benchmark，以准确定位 TTFT 回退来源。
